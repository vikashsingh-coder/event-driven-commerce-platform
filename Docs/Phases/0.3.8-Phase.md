# 7. Request Context

Create:

```text
packages/observability/src/request-context/context.ts
```

```typescript
import { AsyncLocalStorage } from "node:async_hooks";

export interface RequestContext {
  requestId: string;
  correlationId: string;
  traceId?: string;
}

const storage = new AsyncLocalStorage<RequestContext>();

export function runWithContext<T>(
  context: RequestContext,
  callback: () => T,
): T {
  return storage.run(context, callback);
}

export function getRequestContext(): RequestContext | undefined {
  return storage.getStore();
}

export function getRequestId(): string | undefined {
  return storage.getStore()?.requestId;
}

export function getCorrelationId(): string | undefined {
  return storage.getStore()?.correlationId;
}

export function getTraceId(): string | undefined {
  return storage.getStore()?.traceId;
}
```

`AsyncLocalStorage` allows us to access request context deep inside the application without passing `requestId` through every function.

# 8. Request Context Middleware

Create:

```text
packages/observability/src/request-context/middleware.ts
```

```typescript
import type { RequestHandler } from "express";

import { randomUUID } from "node:crypto";

import { runWithContext } from "./context.js";

export const requestContextMiddleware: RequestHandler = (
  request,
  response,
  next,
) => {
  const requestId = request.header("x-request-id") ?? `req_${randomUUID()}`;

  const correlationId =
    request.header("x-correlation-id") ?? `corr_${randomUUID()}`;

  response.setHeader("x-request-id", requestId);

  response.setHeader("x-correlation-id", correlationId);

  runWithContext(
    {
      requestId,
      correlationId,
    },
    () => next(),
  );
};
```

# 12. HTTP Metrics Middleware

Create:

```text
packages/observability/src/metrics/http.ts
```

```typescript
import type { RequestHandler } from "express";

import {
  httpRequestsTotal,
  httpRequestDuration,
  httpActiveRequests,
} from "./registry.js";

export const httpMetricsMiddleware: RequestHandler = (
  request,
  response,
  next,
) => {
  const start = process.hrtime.bigint();

  httpActiveRequests.inc();

  response.on("finish", () => {
    const end = process.hrtime.bigint();

    const duration = Number(end - start) / 1_000_000_000;

    const route = request.route?.path ?? request.path ?? "unknown";

    const labels = {
      method: request.method,

      route,

      status_code: String(response.statusCode),
    };

    httpRequestsTotal.inc(labels);

    httpRequestDuration.observe(labels, duration);

    httpActiveRequests.dec();
  });

  next();
};
```

# 15. Health Checks

Health checks are different from metrics.

We need:

```text
/liveness
/readiness
/health
```

Create:

```text
packages/observability/src/health/health.ts
```

```typescript
export interface HealthCheckResult {
  status: "healthy" | "unhealthy";

  details?: Record<string, unknown>;
}

export interface HealthCheck {
  name: string;

  check(): Promise<HealthCheckResult>;
}

export async function runHealthChecks(checks: HealthCheck[]) {
  const results: Record<string, HealthCheckResult> = {};

  let healthy = true;

  for (const healthCheck of checks) {
    try {
      const result = await healthCheck.check();

      results[healthCheck.name] = result;

      if (result.status !== "healthy") {
        healthy = false;
      }
    } catch (error) {
      healthy = false;

      results[healthCheck.name] = {
        status: "unhealthy",

        details: {
          error: error instanceof Error ? error.message : "Unknown error",
        },
      };
    }
  }

  return {
    status: healthy ? "healthy" : "unhealthy",

    checks: results,
  };
}
```

# 21. Liveness vs Readiness

This distinction is very important for Docker/Kubernetes.

### Liveness

```text
GET /liveness
```

Answers:

> Is the application process alive?

It should be extremely lightweight.

```typescript
app.get("/liveness", (_request, response) => {
  response.json({
    status: "ok",
  });
});
```

Do **not** check the database here.

Otherwise a temporary database outage could cause the orchestrator to kill an otherwise healthy application.

# 24. Tracing Implementation

Create:

```text
packages/observability/src/tracing/tracing.ts
```

```typescript
import { NodeSDK } from "@opentelemetry/sdk-node";

import { OTLPTraceExporter } from "@opentelemetry/exporter-trace-otlp-http";

let sdk: NodeSDK | undefined;

export function initializeTracing(serviceName: string, endpoint: string): void {
  if (sdk) {
    return;
  }

  const exporter = new OTLPTraceExporter({
    url: endpoint,
  });

  sdk = new NodeSDK({
    serviceName,

    traceExporter: exporter,
  });

  sdk.start();
}

export async function shutdownTracing(): Promise<void> {
  if (!sdk) {
    return;
  }

  await sdk.shutdown();

  sdk = undefined;
}
```

# 33. Avoid High-Cardinality Labels

Don't do this:

```text
http_requests_total{
  userId="usr_123"
}
```

or:

```text
http_requests_total{
  orderId="ord_123"
}
```

That can create millions of unique time series.

Good labels:

```text
method
route
status_code
```

Bad labels:

```text
userId
orderId
email
requestId
```

This is an important production Prometheus rule.

## Important: Are we ready for the actual services?

**Yes, with one qualification.**

The shared infrastructure is now sufficiently defined to start implementing the actual application, but before writing large amounts of business code, we should perform a **Phase 0 integration/bootstrap**:

```text
0.3.1 → Config             ✅
0.3.2 → Logger             ✅
0.3.3 → Errors             ✅
0.3.4 → Validation         ✅
0.3.5 → Database           ✅
0.3.6 → Events             ✅
0.3.7 → Security           ✅
0.3.8 → Observability      ✅
             │
             ↓
      Phase 0.4
   Infrastructure
   Integration / Bootstrap
             │
             ↓
      Auth Service
             │
             ↓
     Product Service
             │
             ↓
    Inventory Service
             │
             ↓
      Order Service
             │
             ↓
     Payment Service
             │
             ↓
   Notification Service
```

**The next logical coding phase should therefore be `Phase 0.4 — Infrastructure Bootstrap`**, where we wire these packages together, verify Docker/PostgreSQL/MongoDB/Redis/RabbitMQ connectivity, establish the monorepo service template, and create the first runnable microservice skeleton before implementing business modules.
