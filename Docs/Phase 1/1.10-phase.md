# Phase 1.10 — Shared Platform Integration & Verification

This phase is our quality gate before building the business services. We'll verify that the shared packages developed in Phases 1.1–1.9 work together as one coherent platform, rather than treating each package as an isolated implementation.

One important distinction: the code from our previous phases was provided as implementation guidance, not executed in your repository. So Phase 1.10 must establish what actually compiles, passes tests, and works with real infrastructure before we mark the foundation complete.

## Phase 1.10 plan

1.10.1 — Workspace and package audit

Verify pnpm workspace membership, package names, exports, scripts, dependency versions, and import paths.

1.10.2 — Static checks and unit tests

Run package-level TypeScript checks and tests; fix errors instead of suppressing them.

1.10.3 — Infrastructure integration

Verify PostgreSQL, MongoDB, Redis, and RabbitMQ connectivity, health checks, and shutdown behavior.

1.10.4 — Cross-package smoke test

Exercise configuration → logger → database/Redis/RabbitMQ → HTTP → lifecycle and observability.

1.10.5 — Final verification gate

Record actual pass/fail results, fix critical defects, and decide whether Phase 2 can safely begin.

## 1.10.1 — Audit the monorepo before changing code

Start from the repository root. First, inspect the real workspace rather than creating replacement files based on assumptions.

Run:

```
pnpm --version
node --version
pnpm install --frozen-lockfile
pnpm -r list --depth -1
```

Then inspect the package manifests and workspace configuration:

```
cat pnpm-workspace.yaml
cat package.json
```

On Windows PowerShell, these `cat` commands work as aliases; alternatively, use `Get-Content`.

Confirm that the workspace includes:

```
packages:
  - "apps/*"
  - "packages/*"
```

Keep any existing workspace entries; don't replace the file if it contains additional configuration.

### Expected shared packages

## 1.10.2 — Run the verification gate

After inspecting the manifests, run the checks that actually exist in your root `package.json`.

First, list the available scripts:

```
pnpm run
```

Then run the existing package tests and typechecks. For packages following the scripts proposed in our earlier phases, these commands are examples:

```
pnpm --filter @ecommerce/config typecheck
pnpm --filter @ecommerce/config test

pnpm --filter @ecommerce/logger typecheck
pnpm --filter @ecommerce/logger test

pnpm --filter @ecommerce/database typecheck
pnpm --filter @ecommerce/database test

pnpm --filter @ecommerce/http typecheck
pnpm --filter @ecommerce/http test

pnpm --filter @ecommerce/auth typecheck
pnpm --filter @ecommerce/auth test

pnpm --filter @ecommerce/lifecycle typecheck
pnpm --filter @ecommerce/lifecycle test
```

Run the Redis and RabbitMQ checks using their actual package names and scripts. If any command fails because a script or package doesn't exist, record that as an audit finding rather than silently skipping it.

Once individual checks pass, run workspace-wide checks if the root scripts support them:

```
pnpm -r --if-present typecheck
pnpm -r --if-present test
```

These commands only invoke scripts named `typecheck` and `test`; they won't discover every possible script name. Also, successful unit tests do not establish that real infrastructure connections work.

## 1.10.3 — Verify real infrastructure

Start your existing infrastructure using the Compose file configured for this repository:

```
docker compose config
docker compose up -d
docker compose ps
```

Check container health and logs:

```
docker compose ps
docker compose logs --tail=100
```

Verify the following:

- PostgreSQL accepts connections and can execute a simple query.
- MongoDB accepts connections and can execute a ping.
- Redis responds to `PING`.
- RabbitMQ accepts connections and its required exchanges, queues, bindings, and dead-letter topology are present.
- Services report unhealthy dependencies as not ready.
- Resources close correctly when a service receives `SIGTERM`.

Use the actual Compose service names from your configuration. Don't assume every container has a health check configured.

## 1.10.4 — Cross-package smoke test

Once the isolated checks pass, verify a complete service startup and shutdown.

The smoke test should exercise this sequence:

Validated configuration

Logger and request context

Infrastructure connections and health checks

HTTP request, validation, authentication, and metrics

SIGTERM → readiness down → drain work → close resources

Verify at least these failure cases:

1. A required environment variable is missing.
2. A database is unavailable at startup.
3. A readiness check fails while the process is running.
4. A shutdown hook fails or times out.
5. An invalid JWT is rejected without leaking token details.
6. An event handler fails without silently losing the message.
7. A request's correlation ID appears in the corresponding logs.

For messaging, also verify that consumer reconnection, retry behavior, and dead-letter routing match the intended policy. A successful RabbitMQ connection alone is not enough.

## 1.10.5 — Establish the final gate

Use this as the acceptance criterion:

### Acceptance checklist

0/9

Workspace installation succeeds without changing the lockfile unexpectedly

All shared packages resolve through workspace imports

Package typechecks and unit tests pass

Real infrastructure health checks pass

A service starts and exposes working liveness/readiness endpoints

Authentication and request correlation work end to end

RabbitMQ retry and dead-letter behavior is verified

SIGTERM drains work and closes resources in the intended order

Observability metrics are implemented and verified, if Phase 1.9 is complete

This is a manual tracking checklist; checking an item does not run or verify the test.
