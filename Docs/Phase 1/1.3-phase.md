# Phase 1.3 — Shared Database Package

We'll implement reusable database connectivity for your Event-Driven E-Commerce Backend monorepo, building on Phase 1.1 (Configuration) and Phase 1.2 (Structured Logging).

The key architectural rule is: share connection-management code, not database ownership. Each microservice remains responsible for its own data, schema, migrations, and repository logic.

### Responsibilities

- Create and configure database clients.
- Validate connection settings before connecting.
- Connect during service startup.
- Expose readiness checks.
- Log connection and disconnection events without exposing credentials.
- Close pools and clients gracefully during shutdown.
- Support unit and integration tests.

### What this package will not do

- Share one database across every service.
- Execute business queries for services.
- Own database migrations.
- Automatically retry every failed SQL query.
- Treat a successful startup connection as proof that a database will never fail later.

## 4. Implement the PostgreSQL connection pool

A pool reuses database connections rather than opening a new connection for every query.

We'll configure a bounded pool, log unexpected idle-client errors, provide an explicit health check, and expose a shutdown method.

### `packages/database/src/postgres/create-postgres-pool.ts`

```

import { Pool } from "pg";
import type { Logger } from "pino";

export interface CreatePostgresPoolOptions {
  connectionString: string;
  logger: Logger;
  max?: number;
  idleTimeoutMillis?: number;
  connectionTimeoutMillis?: number;
  applicationName?: string;
}

export function createPostgresPool({
  connectionString,
  logger,
  max = 10,
  idleTimeoutMillis = 30_000,
  connectionTimeoutMillis = 2_000,
  applicationName = "ecommerce-service",
}: CreatePostgresPoolOptions) {
  const pool = new Pool({
    connectionString,
    max,
    idleTimeoutMillis,
    connectionTimeoutMillis,
    application_name: applicationName,
  });

  pool.on("error", (error) => {
    logger.error(
      {
        err: error,
        dependency: "postgres",
        applicationName,
      },
      "Unexpected error on an idle PostgreSQL client",
    );
  });

  let closing = false;
  let closePromise: Promise<void> | undefined;

  async function connect(): Promise<void> {
    if (closing) {
      throw new Error("PostgreSQL pool is shutting down");
    }

    const client = await pool.connect();

    try {
      await client.query("SELECT 1");
    } finally {
      client.release();
    }

    logger.info(
      { dependency: "postgres", applicationName },
      "PostgreSQL connection verified",
    );
  }

  async function healthCheck(): Promise<boolean> {
    if (closing) {
      return false;
    }

    let client;

    try {
      client = await pool.connect();
      await client.query("SELECT 1");
      return true;
    } catch {
      return false;
    } finally {
      client?.release();
    }
  }

  function close(): Promise<void> {
    closing = true;
    closePromise ??= pool.end();
    return closePromise;
  }

  return {
    pool,
    connect,
    healthCheck,
    close,
  };
}

export type PostgresDatabase = ReturnType<
  typeof createPostgresPool
>;

```

### Why these choices?

- `max = 10` is a starting default, not a universal production value. Pool sizes must be tuned against database capacity and the number of service replicas.
- `connectionTimeoutMillis` bounds how long the pool waits to establish a connection.
- `idleTimeoutMillis` lets unused connections be retired.
- `healthCheck()` uses `SELECT 1` to verify the database is reachable.
- `close()` prevents new connections through the wrapper and drains the pool through `pool.end()`.

Important: `pool.end()` waits for checked-out clients to be returned. Your service must stop accepting requests and finish or cancel in-flight work before closing the pool.

## 5. Implement the MongoDB client

MongoDB's `MongoClient` manages a connection pool internally. Unlike PostgreSQL's `Pool`, we should generally create one client per service process and reuse it.

### `packages/database/src/mongodb/create-mongo-client.ts`

```

import {
  MongoClient,
  type Db,
  type MongoClientOptions,
} from "mongodb";

import type { Logger } from "pino";

export interface CreateMongoClientOptions {
  uri: string;
  databaseName: string;
  logger: Logger;
  clientOptions?: MongoClientOptions;
}

export function createMongoClient({
  uri,
  databaseName,
  logger,
  clientOptions = {},
}: CreateMongoClientOptions) {
  const client = new MongoClient(uri, {
    appName: "ecommerce-service",
    serverSelectionTimeoutMS: 2_000,
    ...clientOptions,
  });

  let database: Db | undefined;
  let connectPromise: Promise<Db> | undefined;
  let closePromise: Promise<void> | undefined;
  let closing = false;

  async function connect(): Promise<Db> {
    if (closing) {
      throw new Error("MongoDB client is shutting down");
    }

    if (database) {
      return database;
    }

    connectPromise ??= (async () => {
      try {
        await client.connect();

        const db = client.db(databaseName);

        await db.command({ ping: 1 });

        database = db;

        logger.info(
          { dependency: "mongodb", databaseName },
          "MongoDB connection verified",
        );

        return db;
      } catch (error) {
        connectPromise = undefined;
        throw error;
      }
    })();

    return connectPromise;
  }

  async function healthCheck(): Promise<boolean> {
    if (closing || !database) {
      return false;
    }

    try {
      await database.command({ ping: 1 });
      return true;
    } catch {
      return false;
    }
  }

  function close(): Promise<void> {
    closing = true;
    closePromise ??= client.close();
    return closePromise;
  }

  return {
    client,
    connect,
    healthCheck,
    close,
  };
}

export type MongoDatabase = ReturnType<
  typeof createMongoClient
>;

```

### `packages/database/src/mongodb/index.ts`

```

export {
  createMongoClient,
  type CreateMongoClientOptions,
  type MongoDatabase,
} from "./create-mongo-client.js";

```

Design detail: Concurrent calls to `connect()` share the same in-flight promise. That avoids accidentally launching multiple initial connections if multiple startup components request the database simultaneously.

If initial MongoDB connection fails, the failed promise is cleared so a later explicit retry can attempt a new connection. We won't add an unbounded retry loop here; startup orchestration will own retry policy and timeout limits.

## 6. Add a consistent health-check interface

The service health system from Phase 0.4.10 needs a common way to check both database types.

### `packages/database/src/health/database-health.ts`

```

export interface DatabaseHealthCheck {
  name: string;
  check(): Promise<boolean>;
}

export async function runDatabaseHealthCheck(
  check: DatabaseHealthCheck,
): Promise<"up" | "down"> {
  try {
    return (await check.check()) ? "up" : "down";
  } catch {
    return "down";
  }
}

```

This deliberately returns a simple status rather than leaking database errors into the public health response.

The service can register checks like this:

```
import { runDatabaseHealthCheck } from "@ecommerce/database/health";

const status = await runDatabaseHealthCheck({
  name: "postgres",
  check: postgres.healthCheck,
});

logger.info(
  { dependency: "postgres", status },
  "Database health check completed",
);
```

For a production readiness endpoint, apply an overall timeout to dependency checks. The database drivers have their own connection timeouts, but a health endpoint should also have a bounded response time. We'll connect this interface to the shared service bootstrap in Phase 1.8.

    await expect(

### Service startup

In your current Order Service entry point, connect before listening for traffic:

```
import { database } from "./database/index.js";
import { logger } from "./lib/logger.js";

async function start() {
  await database.connect();

  // Create and start the HTTP server here.
  // Do not listen until required dependencies are ready.

  logger.info("Order Service started");
}

start().catch((error: unknown) => {
  logger.error(
    { err: error },
    "Order Service startup failed",
  );

  process.exitCode = 1;
});
```

This is a startup example, not a replacement for your entire entry point. Use the existing Express app and HTTP server from your service template.

### Query through the pool

```
import { database } from "./database/index.js";

const result = await database.pool.query(
  "SELECT $1::text AS message",
  ["database-connected"],
);

console.log(result.rows[0].message);
```

Use parameterized queries rather than concatenating user input into SQL. Repositories and service-specific data-access code will be developed in the business implementation phases.

## 11. Graceful shutdown

The shared package provides `close()`, but the application must coordinate shutdown. Stop accepting traffic and finish in-flight work before closing the database resources.

A simplified example for a service using PostgreSQL:

```
import { database } from "./database/index.js";
import { logger } from "./lib/logger.js";

let shuttingDown = false;

async function shutdown(signal: string) {
  if (shuttingDown) return;
  shuttingDown = true;

  logger.info({ signal }, "Shutdown started");

  try {
    // 1. Mark the service as not ready.
    // 2. Stop accepting new HTTP requests.
    // 3. Wait for in-flight requests to finish.
    // 4. Stop message consumers, if this service has any.
    await database.close();

    logger.info("Database connections closed");
  } catch (error) {
    logger.error(
      { err: error },
      "Error during shutdown",
    );

    process.exitCode = 1;
  }
}

process.once("SIGTERM", () => {
  void shutdown("SIGTERM");
});

process.once("SIGINT", () => {
  void shutdown("SIGINT");
});
```

Don't copy this as a complete production shutdown handler yet. The real handler must also close the HTTP server, Redis, RabbitMQ, and any other resources the service owns. We'll centralize that lifecycle in Phase 1.8 rather than implementing six slightly different versions.

### Architectural takeaway

We've now defined three reusable layers:

```
@ecommerce/config
       ↓
@ecommerce/logger
       ↓
@ecommerce/database
       ↓
Service-specific repositories
```

The database package owns connection lifecycle—not the business data model. Auth, Order, and Payment continue to own their respective PostgreSQL schemas; Product owns its MongoDB collections.
