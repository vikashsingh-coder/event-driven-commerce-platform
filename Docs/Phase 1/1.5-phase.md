# Phase 1.5 — Shared RabbitMQ Package

We’ll build `@ecommerce/rabbitmq`, the shared messaging layer for your event-driven e-commerce backend.

This phase is especially important because your architecture depends on asynchronous communication between Order, Payment, Product, Notification, and Analytics services. A successful HTTP request or database write does not automatically mean a message was safely delivered, so we need explicit publisher confirms, consumer acknowledgements, retry handling, and dead-letter routing.

## 1. Architecture and scope

Producer services

Order · Payment · Product

`@ecommerce/rabbitmq`

Connection · Confirm publishing · Consumer lifecycle · Retry policy

RabbitMQ

Durable exchanges · Queues · Bindings · Dead-letter routing

Consumer services

Notification · Analytics · Order · Payment

We’ll use `amqplib`, with TypeScript types from `@types/amqplib`.

The package will provide:

- A reusable RabbitMQ connection manager.
- Confirm-channel publishing with persistent messages.
- A standard versioned event envelope.
- Durable exchange, queue, and binding declarations.
- Manual acknowledgement and rejection helpers.
- Retry queues with a bounded retry policy and dead-letter handling.
- Structured logging and graceful shutdown.
- Unit tests plus verification against your local RabbitMQ container.

Delivery guarantee: RabbitMQ publisher confirms and consumer acknowledgements help establish reliable message transfer, but they do not create end-to-end exactly-once processing. Consumers must still be idempotent, and database updates that must not be lost alongside events will eventually need an outbox pattern.

## 3. Define a standard event envelope

Every service should publish events with a consistent shape. This makes events traceable, versionable, and easier to consume across services.

### Step 3 — `packages/rabbitmq/src/events/event-envelope.ts`

```

import { randomUUID } from "node:crypto";

export interface EventEnvelope<TPayload = unknown> {
  id: string;
  type: string;
  version: number;
  occurredAt: string;
  source: string;
  correlationId?: string;
  causationId?: string;
  payload: TPayload;
}

export interface CreateEventOptions<TPayload> {
  type: string;
  version?: number;
  source: string;
  payload: TPayload;
  correlationId?: string;
  causationId?: string;
}

export function createEvent<TPayload>(
  options: CreateEventOptions<TPayload>
): EventEnvelope<TPayload> {
  if (!options.type.trim()) {
    throw new Error("Event type is required");
  }

  if (!options.source.trim()) {
    throw new Error("Event source is required");
  }

  const version = options.version ?? 1;

  if (!Number.isSafeInteger(version) || version < 1) {
    throw new Error("Event version must be a positive integer");
  }

  return {
    id: randomUUID(),
    type: options.type,
    version,
    occurredAt: new Date().toISOString(),
    source: options.source,
    ...(options.correlationId
      ? { correlationId: options.correlationId }
      : {}),
    ...(options.causationId
      ? { causationId: options.causationId }
      : {}),
    payload: options.payload
  };
}

```

Example event:

```
const event = createEvent({
  type: "order.created",
  source: "order-service",
  correlationId: requestId,
  payload: {
    orderId: "order_123",
    customerId: "customer_456",
    totalAmount: 2499
  }
});
```

`id` identifies the event; `correlationId` links work across services; `causationId` identifies the event or command that caused this event. Consumers should use `id` for deduplication, with the deduplication record stored durably where correctness requires it.

## 4. Implement connection lifecycle

### Step 4 — `packages/rabbitmq/src/connection.ts`

This manager owns one RabbitMQ connection per service process and provides a confirm channel for publishing plus regular channels for consuming.

```

import amqp from "amqplib";
import type {
  Channel,
  ConfirmChannel,
  Connection
} from "amqplib";
import type { Logger } from "pino";

export interface RabbitMQOptions {
  url: string;
  logger: Logger;
  serviceName: string;
}

export interface RabbitMQConnection {
  connect(): Promise<void>;
  createConfirmChannel(): Promise<ConfirmChannel>;
  createChannel(): Promise<Channel>;
  close(): Promise<void>;
}

export function createRabbitMQConnection(
  options: RabbitMQOptions
): RabbitMQConnection {
  const { url, logger, serviceName } = options;

  let connection: Connection | undefined;
  let connecting: Promise<void> | undefined;
  let closing = false;
  let closePromise: Promise<void> | undefined;

  const connect = async (): Promise<void> => {
    if (closing) {
      throw new Error("RabbitMQ connection is closing");
    }

    if (connection) {
      return;
    }

    if (connecting) {
      return connecting;
    }

    connecting = (async () => {
      try {
        const candidate = await amqp.connect(url);

        if (closing) {
          await candidate.close();
          throw new Error("RabbitMQ connection closed during startup");
        }

        candidate.on("error", (error: Error) => {
          logger.error(
            { err: error, dependency: "rabbitmq", service: serviceName },
            "RabbitMQ connection error"
          );
        });

        candidate.on("close", () => {
          if (!closing) {
            connection = undefined;
            logger.error(
              { dependency: "rabbitmq", service: serviceName },
              "RabbitMQ connection closed unexpectedly"
            );
          }
        });

        connection = candidate;

        logger.info(
          { dependency: "rabbitmq", service: serviceName },
          "RabbitMQ connected"
        );
      } catch (error) {
        connecting = undefined;
        throw error;
      }
    })();

    return connecting;
  };

  const getConnection = async (): Promise<Connection> => {
    await connect();

    if (!connection || closing) {
      throw new Error("RabbitMQ connection is unavailable");
    }

    return connection;
  };

  const createConfirmChannel = async (): Promise<ConfirmChannel> => {
    const activeConnection = await getConnection();
    return activeConnection.createConfirmChannel();
  };

  const createChannel = async (): Promise<Channel> => {
    const activeConnection = await getConnection();
    return activeConnection.createChannel();
  };

  const close = (): Promise<void> => {
    if (closePromise) {
      return closePromise;
    }

    closing = true;

    closePromise = (async () => {
      await connecting?.catch(() => undefined);

      const activeConnection = connection;
      connection = undefined;

      if (activeConnection) {
        await activeConnection.close();
      }

      logger.info(
        { dependency: "rabbitmq", service: serviceName },
        "RabbitMQ connection closed"
      );
    })();

    return closePromise;
  };

  return {
    connect,
    createConfirmChannel,
    createChannel,
    close
  };
}

```

Important lifecycle boundary: This manager doesn't silently reconnect a closed connection or restore channels and consumers. RabbitMQ channels become invalid when their connection closes. The service lifecycle must detect failure and recreate the connection, channels, topology, and consumers. We'll address operational recovery in the resilience phase rather than pretending this basic manager provides automatic recovery.

## 5. Implement reliable publishing

### Step 5 — `packages/rabbitmq/src/publisher.ts`

Publishing uses a confirm channel, persistent delivery mode, and a bounded timeout. It also respects channel write backpressure so a producer does not keep flooding the client buffer when RabbitMQ is slow.

```

import type { ConfirmChannel, Options } from "amqplib";

import type { EventEnvelope } from "./events/event-envelope.js";

export interface PublishEventOptions {
  exchange: string;
  routingKey: string;
  mandatory?: boolean;
  timeoutMs?: number;
}

export async function publishEvent<T>(
  channel: ConfirmChannel,
  event: EventEnvelope<T>,
  options: PublishEventOptions
): Promise<void> {
  const {
    exchange,
    routingKey,
    mandatory = true,
    timeoutMs = 5000
  } = options;

  if (!Number.isSafeInteger(timeoutMs) || timeoutMs <= 0) {
    throw new Error("timeoutMs must be a positive integer");
  }

  const body = Buffer.from(JSON.stringify(event));

  const messageOptions: Options.Publish = {
    persistent: true,
    contentType: "application/json",
    messageId: event.id,
    type: event.type,
    timestamp: Date.parse(event.occurredAt),
    appId: event.source,
    mandatory,
    headers: {
      eventVersion: event.version,
      ...(event.correlationId
        ? { correlationId: event.correlationId }
        : {}),
      ...(event.causationId
        ? { causationId: event.causationId }
        : {})
    }
  };

  await new Promise<void>((resolve, reject) => {
    let settled = false;
    let timer: ReturnType<typeof setTimeout> | undefined;

    const finish = (error?: Error | null) => {
      if (settled) return;
      settled = true;

      if (timer) clearTimeout(timer);
      channel.removeListener("return", onReturn);

      if (error) reject(error);
      else resolve();
    };

    const onReturn = (message: {
      properties: { messageId?: string };
      fields: { routingKey: string };
    }) => {
      if (message.properties.messageId === event.id) {
        finish(
          new Error(
            `RabbitMQ returned unroutable event ${event.id} for ${routingKey}`
          )
        );
      }
    };

    timer = setTimeout(() => {
      finish(new Error(`RabbitMQ publish timed out for event ${event.id}`));
    }, timeoutMs);

    channel.on("return", onReturn);

    try {
      channel.publish(
        exchange,
        routingKey,
        body,
        messageOptions,
        (error) => finish(error)
      );
    } catch (error) {
      finish(
        error instanceof Error ? error : new Error("Publish failed")
      );
    }
  });
}

```

A few important details:

- A publisher confirm indicates RabbitMQ accepted responsibility for the publish; it doesn't mean a consumer completed its work.
- `mandatory: true` allows an unroutable message to be returned. The publisher fails that attempt rather than silently treating the event as delivered.
- If the timeout fires, the broker's outcome may be unknown. Retrying may duplicate the event, so consumers need idempotency.
- Use a dedicated publisher confirm channel per publishing workload and avoid unlimited concurrent publishing. The timeout is not a substitute for a complete channel shutdown policy.

## 6. Declare durable retry topology

We'll use a delayed retry queue with dead-letter routing. This avoids keeping failed messages in a tight, immediate retry loop.

### Step 6 — `packages/rabbitmq/src/topology/declare-retry-topology.ts`

```

import type { Channel } from "amqplib";

export interface RetryTopologyOptions {
  exchange: string;
  queue: string;
  routingKey: string;
  retryDelayMs?: number;
}

export async function declareRetryTopology(
  channel: Channel,
  options: RetryTopologyOptions
): Promise<void> {
  const {
    exchange,
    queue,
    routingKey,
    retryDelayMs = 10_000
  } = options;

  if (!Number.isSafeInteger(retryDelayMs) || retryDelayMs <= 0) {
    throw new Error("retryDelayMs must be a positive integer");
  }

  const retryExchange = `${exchange}.retry`;
  const deadLetterExchange = `${exchange}.dlx`;
  const retryQueue = `${queue}.retry`;
  const deadLetterQueue = `${queue}.dlq`;
  const retryRoutingKey = `${routingKey}.retry`;

  await channel.assertExchange(exchange, "topic", { durable: true });
  await channel.assertExchange(retryExchange, "direct", { durable: true });
  await channel.assertExchange(deadLetterExchange, "direct", {
    durable: true
  });

  await channel.assertQueue(queue, {
    durable: true,
    arguments: {
      "x-dead-letter-exchange": retryExchange,
      "x-dead-letter-routing-key": retryRoutingKey
    }
  });

  await channel.bindQueue(queue, exchange, routingKey);

  await channel.assertQueue(retryQueue, {
    durable: true,
    arguments: {
      "x-message-ttl": retryDelayMs,
      "x-dead-letter-exchange": exchange,
      "x-dead-letter-routing-key": routingKey
    }
  });

  await channel.bindQueue(
    retryQueue,
    retryExchange,
    retryRoutingKey
  );

  await channel.assertQueue(deadLetterQueue, { durable: true });
  await channel.bindQueue(
    deadLetterQueue,
    deadLetterExchange,
    routingKey
  );
}

```

This creates three queues for a consumer:

- `orders.created` — the main queue.
- `orders.created.retry` — messages wait here for the configured TTL.
- `orders.created.dlq` — permanently failed messages, available for investigation or controlled replay.

Use a dedicated queue per logical consumer, even when multiple consumers subscribe to the same event type. For example, Order and Analytics should not compete for messages in the same queue if both must independently process each event.

Operational note: RabbitMQ queue arguments are part of the topology contract. If a queue already exists with incompatible arguments, redeclaration will fail. Update topology through a controlled migration rather than deleting production queues to make declarations pass.

## 7. Implement the consumer with bounded retries

The consumer will acknowledge a message only after its handler succeeds. When the handler fails, it will reject the message without requeueing it, allowing the main queue's dead-letter configuration to route it to the retry queue. After the retry limit is reached, it will publish the original message to the dead-letter exchange and acknowledge the original only after the publish is confirmed.

### Step 7 — `packages/rabbitmq/src/consumer/consume-with-retry.ts`

```

import type {
  ConfirmChannel,
  ConsumeMessage
} from "amqplib";
import type { Logger } from "pino";

export interface ConsumeWithRetryOptions {
  channel: ConfirmChannel;
  queue: string;
  deadLetterExchange: string;
  deadLetterRoutingKey: string;
  logger: Logger;
  serviceName: string;
  maxRetries?: number;
  handler(message: ConsumeMessage): Promise<void>;
}

export function getDeadLetterCount(
  message: ConsumeMessage,
  queue: string
): number {
  const deaths = message.properties.headers?.["x-death"];

  if (!Array.isArray(deaths)) {
    return 0;
  }

  return deaths.reduce((total: number, death: unknown) => {
    if (!death || typeof death !== "object") {
      return total;
    }

    const entry = death as { queue?: unknown; count?: unknown };

    if (
      entry.queue === queue &&
      typeof entry.count === "number"
    ) {
      return total + entry.count;
    }

    return total;
  }, 0);
}

function publishToDeadLetter(
  channel: ConfirmChannel,
  message: ConsumeMessage,
  exchange: string,
  routingKey: string
): Promise<void> {
  return new Promise((resolve, reject) => {
    const headers = {
      ...message.properties.headers,
      "x-original-exchange": message.fields.exchange,
      "x-original-routing-key": message.fields.routingKey
    };

    const accepted = channel.publish(
      exchange,
      routingKey,
      message.content,
      {
        persistent: true,
        mandatory: true,
        contentType: message.properties.contentType,
        contentEncoding: message.properties.contentEncoding,
        correlationId: message.properties.correlationId,
        messageId: message.properties.messageId,
        type: message.properties.type,
        appId: message.properties.appId,
        timestamp: message.properties.timestamp,
        headers
      },
      (error) => {
        if (error) reject(error);
        else resolve();
      }
    );

    // Backpressure is handled by the publisher flow control policy.
    // Do not interpret `accepted` as a broker confirmation.
    void accepted;
  });
}

export async function consumeWithRetry(
  options: ConsumeWithRetryOptions
): Promise<void> {
  const {
    channel,
    queue,
    deadLetterExchange,
    deadLetterRoutingKey,
    logger,
    serviceName,
    maxRetries = 3,
    handler
  } = options;

  if (!Number.isSafeInteger(maxRetries) || maxRetries < 0) {
    throw new Error("maxRetries must be a non-negative integer");
  }

  await channel.prefetch(10);

  await channel.consume(
    queue,
    async (message) => {
      if (!message) {
        logger.warn(
          { queue, service: serviceName },
          "RabbitMQ consumer was cancelled by the broker"
        );
        return;
      }

      try {
        await handler(message);
        channel.ack(message);
      } catch (error) {
        const retries = getDeadLetterCount(message, queue);

        logger.error(
          {
            err: error,
            queue,
            service: serviceName,
            messageId: message.properties.messageId,
            retries,
            maxRetries
          },
          "RabbitMQ message handler failed"
        );

        if (retries < maxRetries) {
          // The queue's DLX configuration routes this to the retry queue.
          channel.nack(message, false, false);
          return;
        }

        try {
          await publishToDeadLetter(
            channel,
            message,
            deadLetterExchange,
            deadLetterRoutingKey
          );

          // Acknowledge only after the DLQ publish is confirmed.
          channel.ack(message);
        } catch (deadLetterError) {
          logger.fatal(
            {
              err: deadLetterError,
              queue,
              service: serviceName,
              messageId: message.properties.messageId
            },
            "Dead-letter publish failed; preserving original message"
          );

          // Requeueing preserves the message, but can repeatedly fail if
          // the DLQ remains unavailable. Alert and recover operationally.
          channel.nack(message, false, true);
        }
      }
    },
    { noAck: false }
  );
}

```

### Important retry semantics

With `maxRetries: 3`, the intended flow is one original delivery plus up to three retry deliveries, then dead-lettering. RabbitMQ's `x-death` header tracks dead-letter history, so validate this exact behavior against the queue topology and RabbitMQ version you're running.

There is one production hardening item to add before treating this as fully reliable: the dead-letter publisher should handle `mandatory` returns and publisher backpressure explicitly. Publisher confirms alone do not prove a message was routed to the intended DLQ. In production, use a bounded in-flight publisher implementation that handles both confirms and returns, and ensure a failed DLQ publish cannot create a hot requeue loop. The snippet above establishes the core flow, but should not be considered the final failure-proof implementation.

Create `apps/order-service/src/messaging/index.ts`:

```
import {
  createRabbitMQConnection,
  createEvent,
  declareRetryTopology,
  publishEvent
} from "@ecommerce/rabbitmq";

import { config } from "../config/index.js";
import { logger } from "../lib/logger.js";

export const rabbitmq = createRabbitMQConnection({
  url: config.dependencies.RABBITMQ_URL,
  logger,
  serviceName: config.service.name
});

export async function initializeMessaging(): Promise<void> {
  await rabbitmq.connect();

  const channel = await rabbitmq.createChannel();

  try {
    await declareRetryTopology(channel, {
      exchange: "ecommerce.events",
      queue: "orders.created",
      routingKey: "orders.created",
      retryDelayMs: 10_000
    });
  } finally {
    await channel.close();
  }
}

export async function publishOrderCreated(
  orderId: string,
  customerId: string,
  totalAmount: number,
  correlationId?: string
): Promise<void> {
  const channel = await rabbitmq.createConfirmChannel();

  try {
    await channel.assertExchange("ecommerce.events", "topic", {
      durable: true
    });

    const event = createEvent({
      type: "order.created",
      source: "order-service",
      correlationId,
      payload: {
        orderId,
        customerId,
        totalAmount
      }
    });

    await publishEvent(channel, event, {
      exchange: "ecommerce.events",
      routingKey: "orders.created"
    });
  } finally {
    await channel.close();
  }
}
```

This is an integration example, not a complete order workflow. For production traffic, reuse a long-lived confirm channel instead of opening and closing one for every event. Also, only publish `order.created` after the order has been durably recorded—and use the transactional outbox pattern when a database commit and event publication must not get out of sync.

### Consumer example

A consumer can initialize the same topology and register its handler:

```
import {
  consumeWithRetry,
  declareRetryTopology
} from "@ecommerce/rabbitmq";

const channel = await rabbitmq.createConfirmChannel();

await declareRetryTopology(channel, {
  exchange: "ecommerce.events",
  queue: "notifications.orders-created",
  routingKey: "orders.created",
  retryDelayMs: 10_000
});

await consumeWithRetry({
  channel,
  queue: "notifications.orders-created",
  deadLetterExchange: "ecommerce.events.dlx",
  deadLetterRoutingKey: "orders.created",
  logger,
  serviceName: "notification-service",
  maxRetries: 3,
  handler: async (message) => {
    const event = JSON.parse(message.content.toString());

    if (event.type !== "order.created") {
      throw new Error("Unsupported event type");
    }

    // Invoke the notification application service here.
    // Make the operation idempotent using event.id.
  }
});
```

The consumer should use its own queue, even if it listens to the same routing key as another service. For example, Analytics must have a separate queue so Notification consuming a message cannot remove it from Analytics' workload.

## 12. Two hardening fixes before calling this production-ready

The core implementation above is a starting point. Before relying on it for real order and payment traffic, address these issues:

1. Connection recovery: In `connection.ts`, clear the `connecting` promise after a successful connection has been assigned. Otherwise, after an unexpected close, future calls may reuse an already-resolved promise rather than establishing a new connection. Recovery must recreate channels, topology, and consumers too.
2. Publisher flow control and DLQ safety: Respect `channel.publish()` backpressure by limiting in-flight messages and waiting for the channel's `drain` event when needed. For DLQ publishing, handle both publisher confirms and mandatory returns before acknowledging the original. If DLQ publication repeatedly fails, stop or pause the consumer and alert rather than immediately requeueing into a hot loop.

These safeguards are important because the worst failure mode isn't an obvious crash—it's losing an event or repeatedly processing the same business operation without noticing.
