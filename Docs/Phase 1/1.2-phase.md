# Phase 1.2 — Shared Structured Logging Package

We'll implement a reusable logging package for your Event-Driven E-Commerce Backend monorepo. All six services—Auth, Product, Order, Payment, Notification, and Analytics—will use the same logging conventions.

The objective is to make logs useful for debugging distributed workflows, investigating payment failures, and tracing events across services without leaking secrets or personal data.

## 1. What we're building

Microservice

### Technology choice

We'll use Pino, a fast structured logger for Node.js.

Our rules:

- Log structured objects, not strings assembled by concatenation.
- Use `debug`, `info`, `warn`, and `error` consistently.
- Include service name and environment automatically.
- Redact passwords, tokens, cookies, and payment secrets.
- Carry correlation IDs across HTTP requests and asynchronous events.
- Write logs to standard output/error so Docker and centralized log platforms can collect them.
- Never log payment credentials, access tokens, or full sensitive request bodies.

## 4. Implement request context

A correlation ID lets us connect logs belonging to one request as it moves through the system.

For example:

```
Order Service
  requestId: req-123
       │
       ├── Order created
       │
       └── RabbitMQ event
                  │
                  ▼
Notification Service
  requestId: req-123
```

The request ID can be propagated in event metadata when publishing messages. A consumer should restore it into its own context when processing that message.

### `packages/logger/src/request-context.ts`

```

import { AsyncLocalStorage } from "node:async_hooks";

export interface RequestContext {
  requestId: string;
  correlationId?: string;
  traceId?: string;
}

const requestContextStorage =
  new AsyncLocalStorage<RequestContext>();

export function runWithRequestContext<T>(
  context: RequestContext,
  callback: () => T,
): T {
  return requestContextStorage.run(context, callback);
}

export function getRequestContext():
  | RequestContext
  | undefined {
  return requestContextStorage.getStore();
}

```

Why `AsyncLocalStorage`? It carries context through supported asynchronous execution without manually passing a request ID into every function. It does not automatically propagate context between separate processes or across RabbitMQ; we'll explicitly carry the identifiers in event metadata.

## 5. Implement the shared logger

### `packages/logger/src/logger.ts`

This is the main implementation. It creates JSON logs, injects service metadata, attaches request context, and redacts sensitive fields.

```

import pino, {
  type DestinationStream,
  type Logger,
  type LoggerOptions,
} from "pino";

import { getRequestContext } from "./request-context.js";

export type AppLogLevel =
  | "fatal"
  | "error"
  | "warn"
  | "info"
  | "debug"
  | "trace"
  | "silent";

export interface CreateLoggerOptions {
  serviceName: string;
  environment: "development" | "test" | "production";
  level?: AppLogLevel;
  pretty?: boolean;
  destination?: DestinationStream;
}

const REDACT_PATHS = [
  "password",
  "*.password",
  "req.headers.authorization",
  "request.headers.authorization",
  "headers.authorization",
  "authorization",
  "accessToken",
  "refreshToken",
  "*.accessToken",
  "*.refreshToken",
  "token",
  "*.token",
  "secret",
  "*.secret",
  "client_secret",
  "cookie",
  "cookies",
  "set-cookie",
  "RAZORPAY_KEY_SECRET",
  "RAZORPAY_WEBHOOK_SECRET",
  "STRIPE_SECRET_KEY",
  "STRIPE_WEBHOOK_SECRET",
  "JWT_ACCESS_SECRET",
  "JWT_REFRESH_SECRET",
  "DATABASE_URL",
  "MONGODB_URL",
  "REDIS_URL",
  "RABBITMQ_URL",
];

export function createLogger(
  options: CreateLoggerOptions,
): Logger {
  const {
    serviceName,
    environment,
    level = environment === "development" ? "debug" : "info",
    pretty = environment === "development",
    destination,
  } = options;

  const loggerOptions: LoggerOptions = {
    level,

    base: {
      service: serviceName,
      environment,
    },

    timestamp: pino.stdTimeFunctions.isoTime,

    redact: {
      paths: REDACT_PATHS,
      censor: "[REDACTED]",
    },

    serializers: {
      err: pino.stdSerializers.err,
    },

    mixin() {
      return getRequestContext() ?? {};
    },
  };

  if (destination) {
    return pino(loggerOptions, destination);
  }

  if (pretty && environment !== "production") {
    return pino({
      ...loggerOptions,
      transport: {
        target: "pino-pretty",
        options: {
          colorize: true,
          translateTime: "SYS:standard",
          singleLine: true,
          ignore: "pid,hostname",
        },
      },
    });
  }

  return pino(loggerOptions);
}

```

### Important design details

- JSON by default: production logs are machine-readable.
- Pretty logs locally: easier to scan while developing.
- Context injection: every log call can include the current request and correlation IDs.
- Redaction: known sensitive field paths are replaced with `[REDACTED]`.
- Errors: Pino's error serializer records useful error details and stack traces.

Redaction is a safety net, not permission to log arbitrary objects. For example, avoid passing entire HTTP request bodies or payment-provider responses to the logger. Sensitive values nested in unknown structures may not match a configured redaction path.

Use it in application code:

```

import { logger } from "./lib/logger.js";

logger.info("Order service initialized");

logger.info(
  {
    orderId: "order-123",
    event: "order.created",
  },
  "Order created",
);

logger.error(
  {
    err: new Error("Database connection failed"),
    dependency: "postgres",
  },
  "Failed to connect to dependency",
);

```

Prefer structured fields for values you may need to filter later. Avoid logging customer names, email addresses, payment details, or authentication tokens unless there is a clear, reviewed need.

## 8. Add tests for the logger

We need to prove that structured logging and redaction actually work, not just that TypeScript compiles.

### `packages/logger/tests/logger.test.ts`

```

import { Writable } from "node:stream";
import { afterEach, describe, expect, it } from "vitest";

import { createLogger } from "../src/logger.js";

function createCapture() {
  const chunks: Buffer[] = [];

  const destination = new Writable({
    write(chunk, _encoding, callback) {
      chunks.push(Buffer.from(chunk));
      callback();
    },
  });

  return {
    destination,
    read() {
      return chunks
        .join("")
        .trim()
        .split("\n")
        .filter(Boolean)
        .map((line) => JSON.parse(line) as Record<string, unknown>);
    },
  };
}

describe("createLogger", () => {
  let closeLogger: (() => void) | undefined;

  afterEach(() => {
    closeLogger?.();
    closeLogger = undefined;
  });

  it("adds service metadata and structured fields", () => {
    const capture = createCapture();

    const logger = createLogger({
      serviceName: "order-service",
      environment: "test",
      level: "info",
      pretty: false,
      destination: capture.destination,
    });

    closeLogger = () => logger.flush();

    logger.info(
      { orderId: "order-123" },
      "Order created",
    );

    const [entry] = capture.read();

    expect(entry).toMatchObject({
      service: "order-service",
      environment: "test",
      level: 30,
      orderId: "order-123",
      msg: "Order created",
    });

    expect(entry.time).toBeDefined();
  });

  it("redacts sensitive fields", () => {
    const capture = createCapture();

    const logger = createLogger({
      serviceName: "payment-service",
      environment: "test",
      level: "info",
      pretty: false,
      destination: capture.destination,
    });

    closeLogger = () => logger.flush();

    logger.info(
      {
        password: "super-secret-password",
        authorization: "Bearer private-token",
        orderId: "order-123",
      },
      "Processing order",
    );

    const [entry] = capture.read();

    expect(entry.password).toBe("[REDACTED]");
    expect(entry.authorization).toBe("[REDACTED]");
    expect(entry.orderId).toBe("order-123");

    const serialized = JSON.stringify(entry);

    expect(serialized).not.toContain("super-secret-password");
    expect(serialized).not.toContain("private-token");
  });

  it("respects the configured log level", () => {
    const capture = createCapture();

    const logger = createLogger({
      serviceName: "order-service",
      environment: "test",
      level: "warn",
      pretty: false,
      destination: capture.destination,
    });

    closeLogger = () => logger.flush();

    logger.info("This should be filtered");
    logger.warn("This should be logged");

    const entries = capture.read();

    expect(entries).toHaveLength(1);
    expect(entries[0].msg).toBe("This should be logged");
  });
});

```

The `destination` option lets tests capture log output without writing to the terminal. It also makes it possible to verify that secrets are redacted before the output is emitted.

## 9. Connect request context to the logger

The logger now reads request context automatically. Let's test the complete relationship between them.

Add this test to `packages/logger/tests/request-context.test.ts` or create a dedicated `logger-context.test.ts`.

```

import { Writable } from "node:stream";
import { expect, it } from "vitest";

import {
  createLogger,
  runWithRequestContext,
} from "../src/index.js";

it("adds request context to log entries", () => {
  const chunks: Buffer[] = [];

  const destination = new Writable({
    write(chunk, _encoding, callback) {
      chunks.push(Buffer.from(chunk));
      callback();
    },
  });

  const logger = createLogger({
    serviceName: "order-service",
    environment: "test",
    pretty: false,
    destination,
  });

  runWithRequestContext(
    {
      requestId: "req-123",
      correlationId: "corr-456",
    },
    () => {
      logger.info(
        { orderId: "order-123" },
        "Order created",
      );
    },
  );

  const entry = JSON.parse(
    chunks.join("").trim(),
  ) as Record<string, unknown>;

  expect(entry.requestId).toBe("req-123");
  expect(entry.correlationId).toBe("corr-456");
  expect(entry.orderId).toBe("order-123");

  logger.flush();
});

```

Expected behavior:

```
service       = order-service
environment   = test
requestId     = req-123
correlationId = corr-456
orderId       = order-123
msg           = Order created
```

The request ID and correlation ID are added by the logger's `mixin()` function. You don't need to manually attach them to every log statement.

## 13. Logging conventions for the project

We'll standardize these patterns across the platform.

Good — structured event

```
logger.info(
  { orderId, event: "order.created" },
  "Order created",
);
```

Good — error with context

```
logger.error(
  { err, dependency: "postgres" },
  "Database operation failed",
);
```

Avoid — interpolated messages

```
logger.info(`Order ${orderId} created`);
```

The ID becomes part of the message rather than a dedicated field, making filtering and aggregation harder.

Never — log credentials

```
logger.info({ password, accessToken });
```

Avoid passing credentials or sensitive request bodies to the logger at all, even when redaction is configured.
