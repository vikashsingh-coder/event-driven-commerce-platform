# Phase 1.6 — Shared HTTP Utilities

We'll build `@ecommerce/http`, a shared HTTP foundation for all six services in your event-driven e-commerce monorepo.

The objective is to make every service behave consistently: the same response structure, predictable error handling, request validation, request IDs, and correlation IDs—without duplicating boilerplate in Auth, Product, Order, Payment, Notification, and Analytics.

## 1. What we're building

Incoming HTTP request

Headers · Params · Query · Body

`@ecommerce/http` middleware

Request ID

Correlation ID

Validation

Error handling

Consistent HTTP response

Status · Data or error · Request ID

We'll use Express and Zod, consistent with the existing service architecture and shared configuration package.

The package will include:

- Standard success and error response helpers.
- Typed application errors.
- Express error-handling middleware.
- Zod request-validation middleware.
- Request ID and correlation ID middleware integrated with `@ecommerce/logger`.
- A not-found handler.
- Tests for response formatting, validation, and request context.

One important boundary: these utilities standardize the HTTP layer; they won't replace authentication/authorization, service-specific business logic, or payment webhook signature verification.

## 4. Define consistent API responses

Use one predictable envelope across all services. A success response has `success: true`; an error response has `success: false`.

### Step 3 — `packages/http/src/responses/api-response.ts`

```

import type { Response } from "express";

export interface ApiSuccess<T> {
  success: true;
  message: string;
  data: T;
  meta?: Record<string, unknown>;
}

export interface ApiError {
  success: false;
  error: {
    code: string;
    message: string;
    details?: unknown;
  };
  requestId?: string;
}

export function sendSuccess<T>(
  response: Response,
  data: T,
  options: {
    statusCode?: number;
    message?: string;
    meta?: Record<string, unknown>;
  } = {}
): Response<ApiSuccess<T>> {
  const {
    statusCode = 200,
    message = "Request successful",
    meta
  } = options;

  const body: ApiSuccess<T> = {
    success: true,
    message,
    data,
    ...(meta ? { meta } : {})
  };

  return response.status(statusCode).json(body);
}

export function sendCreated<T>(
  response: Response,
  data: T,
  message = "Resource created"
): Response<ApiSuccess<T>> {
  return sendSuccess(response, data, {
    statusCode: 201,
    message
  });
}

export function sendNoContent(response: Response): Response {
  return response.status(204).end();
}

```

Example response:

```
{
  "success": true,
  "message": "Order retrieved",
  "data": {
    "id": "order_123",
    "status": "pending"
  }
}
```

Avoid returning database records wholesale if they contain internal fields or sensitive information. Map them to explicit API response objects.

## 5. Create typed application errors

### Step 4 — `packages/http/src/errors/app-error.ts`

```

export interface AppErrorOptions {
  statusCode: number;
  code: string;
  message: string;
  details?: unknown;
  expose?: boolean;
  cause?: unknown;
}

export class AppError extends Error {
  readonly statusCode: number;
  readonly code: string;
  readonly details?: unknown;
  readonly expose: boolean;

  constructor(options: AppErrorOptions) {
    super(options.message, { cause: options.cause });

    this.name = "AppError";
    this.statusCode = options.statusCode;
    this.code = options.code;
    this.details = options.details;
    this.expose = options.expose ?? options.statusCode < 500;

    Object.setPrototypeOf(this, new.target.prototype);
  }
}

export function badRequest(
  message = "Invalid request",
  details?: unknown
): AppError {
  return new AppError({
    statusCode: 400,
    code: "BAD_REQUEST",
    message,
    details
  });
}

export function unauthorized(
  message = "Authentication required"
): AppError {
  return new AppError({
    statusCode: 401,
    code: "UNAUTHORIZED",
    message
  });
}

export function forbidden(
  message = "Access denied"
): AppError {
  return new AppError({
    statusCode: 403,
    code: "FORBIDDEN",
    message
  });
}

export function notFound(
  message = "Resource not found"
): AppError {
  return new AppError({
    statusCode: 404,
    code: "NOT_FOUND",
    message
  });
}

export function conflict(
  message = "Resource conflict"
): AppError {
  return new AppError({
    statusCode: 409,
    code: "CONFLICT",
    message
  });
}

export function internalError(
  message = "Internal server error",
  cause?: unknown
): AppError {
  return new AppError({
    statusCode: 500,
    code: "INTERNAL_ERROR",
    message,
    expose: false,
    cause
  });
}

```

Usage example:

```
if (!order) {
  throw notFound("Order not found");
}

if (order.status === "cancelled") {
  throw conflict("Cancelled orders cannot be updated");
}
```

A useful rule: throw typed application errors for expected failures; let the central middleware handle unexpected failures. Never pass raw database or provider error messages directly to clients.

## 6. Add request and correlation IDs

Every request should have an ID that can be searched in logs. A correlation ID helps connect related operations across services.

We'll accept a caller-provided ID only if it matches a restricted format; otherwise, we'll generate a UUID. This avoids allowing arbitrarily long or malformed values into logs and response headers.

### Step 5 — `packages/http/src/types/express.d.ts`

### Step 6 — `packages/http/src/middleware/request-context.ts`

```

import { randomUUID } from "node:crypto";
import type { RequestHandler } from "express";

import { runWithRequestContext } from "@ecommerce/logger";

const SAFE_ID_PATTERN = /^[A-Za-z0-9._:-]{1,128}$/;

function getSafeHeaderId(
  value: string | string[] | undefined
): string | undefined {
  if (typeof value !== "string") {
    return undefined;
  }

  return SAFE_ID_PATTERN.test(value) ? value : undefined;
}

export const requestContextMiddleware: RequestHandler = (
  request,
  response,
  next
) => {
  const requestId =
    getSafeHeaderId(request.header("x-request-id")) ?? randomUUID();

  const correlationId =
    getSafeHeaderId(request.header("x-correlation-id")) ?? requestId;

  request.requestId = requestId;
  request.correlationId = correlationId;

  response.setHeader("x-request-id", requestId);
  response.setHeader("x-correlation-id", correlationId);

  runWithRequestContext(
    { requestId, correlationId },
    () => next()
  );
};

```

This uses the `runWithRequestContext` helper from Phase 1.2. Verify that its signature matches your existing implementation; the intended contract is to execute the callback within the `AsyncLocalStorage` context.

Security note: Request IDs are for observability, not authentication. Never use them as authorization credentials or as proof that a request originated from a trusted service.

## 7. Validate requests with Zod

Instead of manually validating each route, we'll make validation a reusable middleware. Validated input is stored in `request.validated`; route handlers should use that value rather than assuming the original request data is trustworthy.

### Step 7 — `packages/http/src/middleware/validate-request.ts`

```

import type { RequestHandler } from "express";
import type { ZodTypeAny } from "zod";

export interface RequestSchemas {
  body?: ZodTypeAny;
  params?: ZodTypeAny;
  query?: ZodTypeAny;
}

export function validateRequest(
  schemas: RequestSchemas
): RequestHandler {
  return (request, _response, next) => {
    const validated: NonNullable<typeof request.validated> = {};

    for (const part of ["params", "query", "body"] as const) {
      const schema = schemas[part];

      if (!schema) {
        continue;
      }

      const result = schema.safeParse(request[part]);

      if (!result.success) {
        const error = new Error("Request validation failed");

        Object.assign(error, {
          name: "RequestValidationError",
          statusCode: 400,
          code: "VALIDATION_ERROR",
          details: result.error.issues.map((issue) => ({
            path: issue.path.map(String).join("."),
            message: issue.message
          }))
        });

        next(error);
        return;
      }

      validated[part] = result.data;
    }

    request.validated = validated;
    next();
  };
}

```

Example route:

```
import { z } from "zod";
import { validateRequest, sendCreated } from "@ecommerce/http";

const createOrderSchema = z.object({
  customerId: z.string().min(1),
  items: z.array(
    z.object({
      productId: z.string().min(1),
      quantity: z.number().int().positive()
    })
  ).min(1)
});

app.post(
  "/orders",
  validateRequest({ body: createOrderSchema }),
  async (request, response) => {
    const input = request.validated?.body as z.infer<
      typeof createOrderSchema
    >;

    const order = await orderService.create(input);

    return sendCreated(response, order, "Order created");
  }
);
```

For a larger application, prefer a small typed helper that retrieves validated input for each route, so handlers don't need type assertions. This initial middleware establishes the shared behavior; we can strengthen inference as your route typing conventions settle.

## 8. Centralize error handling

### Step 8 — `packages/http/src/middleware/error-handler.ts`

This middleware is the final error boundary for HTTP routes. It logs the actual error internally, but returns only safe error information to the client.

```

import type { ErrorRequestHandler } from "express";
import type { Logger } from "pino";

import { AppError } from "../errors/app-error.js";

interface NormalizedError {
  statusCode: number;
  code: string;
  message: string;
  details?: unknown;
  expose: boolean;
}

function normalizeError(error: unknown): NormalizedError {
  if (error instanceof AppError) {
    return {
      statusCode: error.statusCode,
      code: error.code,
      message: error.message,
      details: error.details,
      expose: error.expose
    };
  }

  if (error && typeof error === "object") {
    const candidate = error as {
      statusCode?: unknown;
      code?: unknown;
      message?: unknown;
      details?: unknown;
    };

    // Supports the validation error produced by validateRequest.
    if (candidate.code === "VALIDATION_ERROR") {
      return {
        statusCode: 400,
        code: "VALIDATION_ERROR",
        message: "Request validation failed",
        details: candidate.details,
        expose: true
      };
    }

    // Don't trust arbitrary error.statusCode values.
    if (
      typeof candidate.statusCode === "number" &&
      candidate.statusCode >= 400 &&
      candidate.statusCode < 500 &&
      Number.isInteger(candidate.statusCode)
    ) {
      return {
        statusCode: candidate.statusCode,
        code:
          typeof candidate.code === "string"
            ? candidate.code
            : "REQUEST_ERROR",
        message:
          typeof candidate.message === "string"
            ? candidate.message
            : "Request failed",
        expose: true
      };
    }
  }

  return {
    statusCode: 500,
    code: "INTERNAL_ERROR",
    message: "Internal server error",
    expose: false
  };
}

export function createErrorHandler(
  logger: Logger
): ErrorRequestHandler {
  return (error, request, response, _next) => {
    if (response.headersSent) {
      // Delegate to Express for an already-started response.
      return _next(error);
    }

    const normalized = normalizeError(error);
    const isServerError = normalized.statusCode >= 500;

    logger[isServerError ? "error" : "warn"](
      {
        err: error,
        requestId: request.requestId,
        correlationId: request.correlationId,
        method: request.method,
        path: request.path,
        statusCode: normalized.statusCode,
        errorCode: normalized.code
      },
      "HTTP request failed"
    );

    return response.status(normalized.statusCode).json({
      success: false,
      error: {
        code: normalized.code,
        message: normalized.expose
          ? normalized.message
          : "Internal server error",
        ...(normalized.expose && normalized.details !== undefined
          ? { details: normalized.details }
          : {})
      },
      ...(request.requestId ? { requestId: request.requestId } : {})
    });
  };
}

```

## 12. Integrate with a service

In each service's existing Express application, register middleware in the correct order:

```
import express from "express";

import {
  requestContextMiddleware,
  notFoundHandler,
  createErrorHandler
} from "@ecommerce/http";

import { logger } from "./lib/logger.js";

const app = express();

// 1. Establish request context before logging or route handling.
app.use(requestContextMiddleware);

// 2. Parse request bodies.
app.use(express.json({ limit: "1mb" }));

// 3. Register service-specific routes here.
// app.use("/api/v1/orders", orderRoutes);

// 4. Handle unmatched routes.
app.use(notFoundHandler);

// 5. Keep error handling last.
app.use(createErrorHandler(logger));

export { app };
```

This is a registration example; keep your existing routes and health endpoints. Also, configure an appropriate body-size limit and verify webhook signature handling uses the raw request body where the payment provider requires it.

### Example route using the shared response contract

```
import { Router } from "express";
import { sendSuccess, notFound } from "@ecommerce/http";

const router = Router();

router.get("/:orderId", async (request, response) => {
  const order = await orderService.findById(request.params.orderId);

  if (!order) {
    throw notFound("Order not found");
  }

  return sendSuccess(response, order, {
    message: "Order retrieved"
  });
});

export default router;
```

With Express 5, rejected promises from async route handlers are forwarded to error middleware. If your project uses Express 4, wrap async handlers or use an async-handler utility so rejected promises reach `next(error)`.

## 13. Security and correctness hardening

Before using this package as the standard across all services, make these two adjustments:

1. Only expose known-safe errors. In `error-handler.ts`, remove the generic branch that exposes any arbitrary error with a `statusCode` between 400 and 499. Only `AppError` and explicitly recognized validation errors should control public error messages. Unknown errors should become a generic 500 response.
2. Test request context propagation. Confirm that `requestId` and `correlationId` appear in logs emitted inside asynchronous route handlers. When publishing RabbitMQ events, explicitly copy the correlation ID into the event envelope—HTTP `AsyncLocalStorage` context does not automatically propagate across message brokers.

For production, also consider redacting or limiting validation details, normalizing malformed JSON errors, and ensuring request IDs are preserved across trusted internal calls without treating caller-supplied IDs as security credentials.
