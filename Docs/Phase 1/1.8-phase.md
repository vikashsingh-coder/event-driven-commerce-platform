# Phase 1.8 — Shared Service Lifecycle & Graceful Shutdown

In Phase 1.8, we’ll build a shared lifecycle package so every microservice starts, becomes ready, handles failures, and shuts down in a consistent way.

The goal is to make your Event-Driven E-Commerce Backend behave like a production service—not just an Express server that happens to connect to databases.

## What we’re building

1\. Start service

Load config → initialize logger → connect dependencies

2\. Become ready

Verify required dependencies → start HTTP server → report readiness

3\. Run service

Serve requests, consume events, and respond to health checks

4\. Graceful shutdown

Stop accepting traffic → stop consumers → drain requests → close resources

The package will coordinate resources created by your existing shared packages:

- `@ecommerce/config` — validated environment configuration
- `@ecommerce/logger` — structured logs
- `@ecommerce/database` — PostgreSQL and MongoDB connections
- `@ecommerce/redis` — Redis client
- `@ecommerce/rabbitmq` — broker connections and consumers
- `@ecommerce/http` — Express middleware and error handling

Important: this package coordinates resource lifecycles; it should not secretly create database or broker clients. Each service remains responsible for initializing its own dependencies and registering how they should be closed.

## 1. Define lifecycle behavior

We’ll use four shutdown phases so dependencies remain available until the components that depend on them have stopped.

| Phase             | Action                              | Examples                             |
| ----------------- | ----------------------------------- | ------------------------------------ |
| `stop-ingress`    | Stop accepting new HTTP connections | HTTP server                          |
| `stop-consumers`  | Stop receiving new broker messages  | RabbitMQ consumers                   |
| `drain`           | Wait for in-flight work to finish   | Active HTTP requests, handlers       |
| `close-resources` | Close infrastructure connections    | RabbitMQ, Redis, PostgreSQL, MongoDB |

Each phase runs in order. Within a phase, hooks run in reverse registration order. Each hook has a timeout so one stuck resource doesn’t block shutdown indefinitely.

## 3. Implement bounded, ordered shutdown

### `packages/lifecycle/src/shutdown.ts`

This manager is responsible for registering cleanup tasks, running them once, logging failures, and enforcing a timeout per task.

```
import type { ShutdownHook, ShutdownHookOptions } from "./types.js";
import { SHUTDOWN_PHASES } from "./types.js";

export interface ShutdownLogger {
  info: (fields: object, message: string) => void;
  warn: (fields: object, message: string) => void;
  error: (fields: object, message: string) => void;
}

interface RegisteredHook extends ShutdownHookOptions {
  callback: ShutdownHook;
  sequence: number;
}

export interface ShutdownOptions {
  logger: ShutdownLogger;
  defaultTimeoutMs?: number;
}

export interface ShutdownReport {
  startedAt: string;
  finishedAt: string;
  durationMs: number;
  failures: Array<{
    name: string;
    phase: string;
    error: string;
  }>;
}

export class ShutdownManager {
  private readonly hooks: RegisteredHook[] = [];
  private readonly logger: ShutdownLogger;
  private readonly defaultTimeoutMs: number;
  private sequence = 0;
  private shutdownPromise?: Promise<ShutdownReport>;

  constructor(options: ShutdownOptions) {
    this.logger = options.logger;
    this.defaultTimeoutMs = options.defaultTimeoutMs ?? 10_000;
  }

  register(
    options: ShutdownHookOptions,
    callback: ShutdownHook
  ): void {
    if (this.shutdownPromise) {
      throw new Error("Cannot register hooks after shutdown has started");
    }

    if (this.hooks.some((hook) => hook.name === options.name)) {
      throw new Error(`Duplicate shutdown hook: ${options.name}`);
    }

    const timeoutMs = options.timeoutMs ?? this.defaultTimeoutMs;

    if (!Number.isInteger(timeoutMs) || timeoutMs <= 0) {
      throw new Error("Shutdown hook timeout must be a positive integer");
    }

    this.hooks.push({
      ...options,
      timeoutMs,
      callback,
      sequence: this.sequence++
    });
  }

  shutdown(reason = "manual"): Promise<ShutdownReport> {
    // Multiple signal handlers or callers share the same shutdown operation.
    if (this.shutdownPromise) {
      return this.shutdownPromise;
    }

    this.shutdownPromise = this.executeShutdown(reason);
    return this.shutdownPromise;
  }

  private async executeShutdown(
    reason: string
  ): Promise<ShutdownReport> {
    const started = Date.now();
    const startedAt = new Date(started).toISOString();
    const failures: ShutdownReport["failures"] = [];

    this.logger.info({ reason }, "Service shutdown started");

    for (const phase of SHUTDOWN_PHASES) {
      const phaseHooks = this.hooks
        .filter((hook) => hook.phase === phase)
        .sort((a, b) => b.sequence - a.sequence);

      for (const hook of phaseHooks) {
        try {
          await this.runWithTimeout(
            hook.callback,
            hook.timeoutMs!,
            hook.name
          );

          this.logger.info(
            { hook: hook.name, phase },
            "Shutdown hook completed"
          );
        } catch (error) {
          const message =
            error instanceof Error ? error.message : String(error);

          failures.push({
            name: hook.name,
            phase,
            error: message
          });

          this.logger.error(
            { hook: hook.name, phase, error: message },
            "Shutdown hook failed"
          );

          // Continue closing other resources even when one hook fails.
        }
      }
    }

    const finished = Date.now();

    const report: ShutdownReport = {
      startedAt,
      finishedAt: new Date(finished).toISOString(),
      durationMs: finished - started,
      failures
    };

    if (failures.length > 0) {
      this.logger.warn(
        { failureCount: failures.length, durationMs: report.durationMs },
        "Service shutdown completed with failures"
      );
    } else {
      this.logger.info(
        { durationMs: report.durationMs },
        "Service shutdown completed"
      );
    }

    return report;
  }

  private runWithTimeout(
    callback: ShutdownHook,
    timeoutMs: number,
    name: string
  ): Promise<void> {
    return new Promise<void>((resolve, reject) => {
      const timer = setTimeout(() => {
        reject(new Error(`Hook "${name}" timed out after ${timeoutMs}ms`));
      }, timeoutMs);

      // Handle synchronous throws and rejected promises.
      Promise.resolve()
        .then(callback)
        .then(resolve, reject)
        .finally(() => clearTimeout(timer));
    });
  }
}
```

Design detail: timing out a hook does not cancel the underlying operation. That’s intentional for a generic package, but your service's final process-level shutdown deadline should be longer than the individual hook timeouts. A timed-out connection close may still be running in the background.

## 4. Implement readiness checks

A process can be running but not ready to serve traffic. For example, the HTTP server may be up while PostgreSQL is disconnected.

### `packages/lifecycle/src/readiness.ts`

```
import type { ReadinessCheck, ReadinessResult } from "./types.js";

export class ReadinessManager {
  private readonly checks = new Map<string, ReadinessCheck>();
  private acceptingTraffic = false;

  register(check: ReadinessCheck): void {
    if (this.checks.has(check.name)) {
      throw new Error(`Duplicate readiness check: ${check.name}`);
    }

    this.checks.set(check.name, check);
  }

  markReady(): void {
    this.acceptingTraffic = true;
  }

  markNotReady(): void {
    this.acceptingTraffic = false;
  }

  async getStatus(): Promise<ReadinessResult> {
    const results = await Promise.all(
      [...this.checks.values()].map(async ({ name, check }) => {
        try {
          return [name, (await check()) ? "up" : "down"] as const;
        } catch {
          return [name, "down"] as const;
        }
      })
    );

    const checks = Object.fromEntries(results) as ReadinessResult["checks"];

    const dependenciesReady = results.every(([, status]) => status === "up");

    return {
      ready: this.acceptingTraffic && dependenciesReady,
      checks
    };
  }
}
```

This gives you two separate controls:

- `markReady()` is called only after startup has succeeded.
- `markNotReady()` immediately makes the service unready during shutdown—even if its dependencies are still healthy.

Readiness checks must be fast and bounded. The database or broker health functions registered here should use short timeouts rather than allowing a health endpoint to hang.

## 5. Compose the service lifecycle

### `packages/lifecycle/src/lifecycle.ts`

```
import { ReadinessManager } from "./readiness.js";
import { ShutdownManager } from "./shutdown.js";
import type {
  ReadinessCheck,
  ShutdownHook,
  ShutdownHookOptions
} from "./types.js";

export interface ServiceLifecycleOptions {
  logger: ConstructorParameters<typeof ShutdownManager>[0]["logger"];
  shutdownTimeoutMs?: number;
}

export class ServiceLifecycle {
  readonly readiness = new ReadinessManager();
  readonly shutdownManager: ShutdownManager;

  private started = false;

  constructor(options: ServiceLifecycleOptions) {
    this.shutdownManager = new ShutdownManager({
      logger: options.logger,
      defaultTimeoutMs: options.shutdownTimeoutMs
    });
  }

  registerReadinessCheck(check: ReadinessCheck): void {
    this.readiness.register(check);
  }

  registerShutdownHook(
    options: ShutdownHookOptions,
    callback: ShutdownHook
  ): void {
    this.shutdownManager.register(options, callback);
  }

  markReady(): void {
    this.started = true;
    this.readiness.markReady();
  }

  async shutdown(reason = "manual") {
    this.readiness.markNotReady();
    this.started = false;

    return this.shutdownManager.shutdown(reason);
  }

  get isStarted(): boolean {
    return this.started;
  }
}
```

## 6. Add process signal handling

### `packages/lifecycle/src/process-signals.ts`

Register signal handlers only once, after the service has registered all its cleanup hooks.

```
import type { ServiceLifecycle } from "./lifecycle.js";

export interface SignalHandlerOptions {
  lifecycle: ServiceLifecycle;
  onComplete?: (exitCode: number) => void;
}

export function installProcessSignalHandlers(
  options: SignalHandlerOptions
): () => void {
  const { lifecycle, onComplete } = options;
  let handlingSignal = false;

  const handleSignal = (signal: NodeJS.Signals) => {
    if (handlingSignal) return;
    handlingSignal = true;

    void lifecycle.shutdown(signal).then((report) => {
      const exitCode = report.failures.length > 0 ? 1 : 0;

      process.exitCode = exitCode;
      onComplete?.(exitCode);
    }).catch(() => {
      process.exitCode = 1;
      onComplete?.(1);
    });
  };

  const onSigterm = () => handleSignal("SIGTERM");
  const onSigint = () => handleSignal("SIGINT");

  process.on("SIGTERM", onSigterm);
  process.on("SIGINT", onSigint);

  return () => {
    process.off("SIGTERM", onSigterm);
    process.off("SIGINT", onSigint);
  };
}
```

Add this export to `src/index.ts`:

```
export {
  installProcessSignalHandlers
} from "./process-signals.js";

export type {
  SignalHandlerOptions
} from "./process-signals.js";
```

Why not call `process.exit()` immediately? It can terminate the process before logs flush or in-flight work completes. We set `process.exitCode` after cleanup instead. In production, the container orchestrator should also have a finite termination grace period; the application must finish within it.

## 7. Add an HTTP server shutdown adapter

There is one important detail with Node's `server.close()`: its callback generally resolves after existing connections have closed. If we await it in `stop-ingress`, we may wait for requests before stopping RabbitMQ consumers.

Instead, initiate server closure during `stop-ingress`, stop consumers next, then await the server-drain promise in `drain`.

### `packages/lifecycle/src/http-server-hooks.ts`

```
import type { Server } from "node:http";
import type { ShutdownHookOptions } from "./types.js";

export interface HttpServerShutdownHooks {
  stopIngress: {
    options: ShutdownHookOptions;
    run: () => void;
  };
  drain: {
    options: ShutdownHookOptions;
    run: () => Promise<void>;
  };
}

export function createHttpServerShutdownHooks(
  server: Server,
  timeoutMs = 10_000
): HttpServerShutdownHooks {
  let closePromise: Promise<void> | undefined;

  return {
    stopIngress: {
      options: {
        name: "http-stop-ingress",
        phase: "stop-ingress",
        timeoutMs
      },
      run: () => {
        if (closePromise) return;

        closePromise = new Promise<void>((resolve, reject) => {
          server.close((error) => {
            if (error) reject(error);
            else resolve();
          });

          // Available on modern Node versions. Do not forcibly close
          // active connections here; let the drain phase handle them.
          server.closeIdleConnections?.();
        });
      }
    },
    drain: {
      options: {
        name: "http-drain",
        phase: "drain",
        timeoutMs
      },
      run: async () => {
        if (closePromise) {
          await closePromise;
        }
      }
    }
  };
}
```

Export it from `src/index.ts`:

```
export {
  createHttpServerShutdownHooks
} from "./http-server-hooks.js";

export type {
  HttpServerShutdownHooks
} from "./http-server-hooks.js";
```

This adapter stops accepting new connections first and waits for the existing HTTP work later. If your Node version supports it, `closeIdleConnections()` helps clean up idle connections. For long-lived connections such as WebSockets, add explicit connection tracking and shutdown handling.

    const second = manager.shutdown("SIGINT");

    expect(second).toBe(first);
    await first;
    expect(close).toHaveBeenCalledOnce();

### Register resources and start the server

The intended startup sequence is:

1. Load validated config and create the logger.
2. Connect required infrastructure.
3. Register each resource's cleanup hook immediately after it is created.
4. Register readiness checks.
5. Start HTTP and register its shutdown hooks.
6. Install process signal handlers and mark the service ready.

Example `apps/order-service/src/main.ts`:

```
import { createServer } from "node:http";
import { app } from "./app.js";
import { config } from "./config/index.js";
import { logger } from "./lib/logger.js";

import {
  ServiceLifecycle,
  createHttpServerShutdownHooks,
  installProcessSignalHandlers
} from "@ecommerce/lifecycle";

// Replace these with the real clients and APIs from your packages.
import { createPostgresPool } from "@ecommerce/database/postgres";
import { createRedisClient } from "@ecommerce/redis";

const lifecycle = new ServiceLifecycle({ logger });

async function start(): Promise<void> {
  try {
    // 1. PostgreSQL
    const postgres = await createPostgresPool({
      connectionString: config.dependencies.DATABASE_URL,
      logger
    });

    lifecycle.registerShutdownHook(
      {
        name: "postgres-pool",
        phase: "close-resources",
        timeoutMs: 8_000
      },
      () => postgres.close()
    );

    lifecycle.registerReadinessCheck({
      name: "postgres",
      check: () => postgres.healthCheck()
    });

    // 2. Redis
    const redis = await createRedisClient({
      url: config.dependencies.REDIS_URL,
      logger
    });

    lifecycle.registerShutdownHook(
      {
        name: "redis-client",
        phase: "close-resources",
        timeoutMs: 5_000
      },
      () => redis.close()
    );

    lifecycle.registerReadinessCheck({
      name: "redis",
      check: () => redis.healthCheck()
    });

    // 3. HTTP server
    const server = createServer(app);

    await new Promise<void>((resolve, reject) => {
      const onError = (error: Error) => {
        server.off("listening", onListening);
        reject(error);
      };

      const onListening = () => {
        server.off("error", onError);
        resolve();
      };

      server.once("error", onError);
      server.once("listening", onListening);
      server.listen(config.service.port);
    });

    const httpHooks = createHttpServerShutdownHooks(server, 10_000);

    lifecycle.registerShutdownHook(
      httpHooks.stopIngress.options,
      httpHooks.stopIngress.run
    );

    lifecycle.registerShutdownHook(
      httpHooks.drain.options,
      httpHooks.drain.run
    );

    // 4. Signal handlers, then readiness.
    installProcessSignalHandlers({ lifecycle });

    lifecycle.markReady();

    logger.info(
      {
        port: config.service.port,
        service: config.service.name
      },
      "Order Service started"
    );
  } catch (error) {
    logger.error({ error }, "Order Service startup failed");

    const report = await lifecycle.shutdown("startup-failure");

    if (report.failures.length > 0) {
      process.exitCode = 1;
    } else {
      process.exitCode = 1;
    }
  }
}

void start();
```

Important integration adjustments:

- The PostgreSQL and Redis factory signatures above are illustrative. Match them to your actual Phase 1.3 and 1.4 implementations.
- The sample assumes those clients expose `close()` and `healthCheck()`. If yours expose `pool.end()`, `client.quit()`, or another API, register the appropriate function.
- The example doesn't yet register RabbitMQ. When adding it, stop consumers in `stop-consumers`, wait for in-flight message handlers to finish, then close the broker connection in `close-resources`.
- If `server.listen()` fails, it is possible no HTTP hooks were registered. The catch block still shuts down any dependencies whose hooks were already registered.
- Do not mark the service ready until every required dependency and consumer topology has been initialized. Optional dependencies need an explicit degraded-mode policy.

For cleaner production code, consider extracting infrastructure startup into a `createOrderService()` function that returns the server and lifecycle manager. This makes startup and shutdown easier to test without importing a side-effectful `main.ts`.

import { Router } from "express";
import type { ServiceLifecycle } from "@ecommerce/lifecycle";

export function createHealthRouter(
  lifecycle: ServiceLifecycle
): Router {
  const router = Router();

  router.get("/live", (_req, res) => {
    res.status(200).json({
      status: "ok"
    });
  });

  router.get("/ready", async (_req, res) => {
    const result = await lifecycle.readiness.getStatus();

    res.status(result.ready ? 200 : 503).json({
      status: result.ready ? "ready" : "not_ready",
      checks: result.checks
    });
  });

  return router;
}
```

Mount it in your app using your existing route-registration pattern. For example, if you use `/health` as the base path:

- `GET /health/live` → `200` when the process is alive.
- `GET /health/ready` → `200` when startup is complete and required checks pass.
- `GET /health/ready` → `503` before readiness or during shutdown.

Use your actual configured Nginx upstream health-check strategy if it differs. Also consider restricting detailed dependency status to internal infrastructure; public endpoints generally should not reveal internal topology.

import { describe, expect, it, vi } from "vitest";
import { ServiceLifecycle } from "../src/lifecycle.js";

describe("ServiceLifecycle", () => {
  const logger = {
    info: vi.fn(),
    warn: vi.fn(),
    error: vi.fn()
  };

  it("starts unready and becomes ready after initialization", async () => {
    const lifecycle = new ServiceLifecycle({ logger });

    lifecycle.registerReadinessCheck({
      name: "database",
      check: () => true
    });

    expect(lifecycle.isStarted).toBe(false);
    expect((await lifecycle.readiness.getStatus()).ready).toBe(false);

    lifecycle.markReady();

    expect(lifecycle.isStarted).toBe(true);
    expect((await lifecycle.readiness.getStatus()).ready).toBe(true);
  });

  it("marks itself unready before shutdown hooks execute", async () => {
    const lifecycle = new ServiceLifecycle({ logger });

    lifecycle.registerReadinessCheck({
      name: "database",
      check: () => true
    });

    lifecycle.markReady();

    let readinessDuringShutdown: boolean | undefined;

    lifecycle.registerShutdownHook(
      {
        name: "observe-readiness",
        phase: "stop-ingress"
      },
      async () => {
        readinessDuringShutdown =
          (await lifecycle.readiness.getStatus()).ready;
      }
    );

    await lifecycle.shutdown("test");

    expect(readinessDuringShutdown).toBe(false);
    expect(lifecycle.isStarted).toBe(false);
  });
});
```

Use fresh logger mocks per test if you expand this suite and want to assert exact log calls; the shared mock object above is sufficient for the basic lifecycle checks.

## Important architecture notes

Before calling this phase production-ready, account for these limitations:

1. Readiness timeouts: the current `ReadinessManager` does not enforce a timeout around each check. Implement bounded checks or add a timeout wrapper before exposing them to orchestration probes.
2. Process deadline: per-hook timeouts don't guarantee a hard overall shutdown deadline. Configure Docker/Kubernetes termination grace periods and test the actual signal behavior.
3. Message processing: RabbitMQ consumer cancellation must be followed by draining in-flight handlers before the broker connection closes. Don't acknowledge messages before their processing succeeds.
4. Database/event consistency: graceful shutdown helps finish work but cannot replace a transactional outbox or idempotent message processing.
5. Repeated shutdown: the manager intentionally shares one shutdown promise. A second signal won't force termination; use an explicit, tested escalation policy if you need one.

Definition of done: the lifecycle package typechecks, its tests pass, and at least one service demonstrates clean startup, readiness transitions, ordered cleanup, and shutdown under a real `SIGTERM`.
