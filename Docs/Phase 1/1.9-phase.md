# Phase 1.9 — Shared Observability & Metrics

In this phase, we’ll give your Event-Driven E-Commerce Backend a consistent way to answer three production questions:

- What is happening? — structured logs from `@ecommerce/logger`
- How healthy is it? — service health and dependency status from Phase 1.8
- How is it performing? — request counts, error rates, latency, and process metrics

The aim is to make it possible to debug slow APIs, failing dependencies, and RabbitMQ processing issues across your six services without inventing a different monitoring approach for each one.

We’ll start with a shared metrics package and Express middleware, then add Prometheus and Grafana configuration. We’ll keep logs and metrics separate: metrics should use bounded labels, while request IDs and detailed error context belong in logs.

## 2. Build the shared metrics registry

Each service process should have one registry and one set of metric instances. Creating a new registry every time `/metrics` is requested would make metrics unreliable.

### `packages/observability/src/metrics.ts`

```
import {
  Registry,
  Counter,
  Histogram,
  Gauge,
  collectDefaultMetrics
} from "prom-client";

export interface MetricsOptions {
  serviceName: string;
  collectDefaultProcessMetrics?: boolean;
}

export function createMetrics(options: MetricsOptions) {
  const { serviceName } = options;

  if (!serviceName.trim()) {
    throw new Error("serviceName must not be empty");
  }

  const registry = new Registry();

  registry.setDefaultLabels({
    service: serviceName
  });

  if (options.collectDefaultProcessMetrics !== false) {
    collectDefaultMetrics({
      register: registry,
      prefix: "ecommerce_"
    });
  }

  const httpRequestsTotal = new Counter({
    name: "ecommerce_http_requests_total",
    help: "Total number of completed HTTP requests",
    labelNames: ["method", "route", "status_code"] as const,
    registers: [registry]
  });

  const httpRequestDurationSeconds = new Histogram({
    name: "ecommerce_http_request_duration_seconds",
    help: "HTTP request duration in seconds",
    labelNames: ["method", "route", "status_code"] as const,
    buckets: [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10],
    registers: [registry]
  });

  const httpRequestsInFlight = new Gauge({
    name: "ecommerce_http_requests_in_flight",
    help: "Number of HTTP requests currently being processed",
    labelNames: ["method"] as const,
    registers: [registry]
  });

  const dependencyHealth = new Gauge({
    name: "ecommerce_dependency_up",
    help: "Whether a dependency was healthy at the last observation (1=up, 0=down)",
    labelNames: ["dependency"] as const,
    registers: [registry]
  });

  const messagesPublishedTotal = new Counter({
    name: "ecommerce_messages_published_total",
    help: "Total number of messages successfully published",
    labelNames: ["exchange", "event_type", "outcome"] as const,
    registers: [registry]
  });

  const messagesConsumedTotal = new Counter({
    name: "ecommerce_messages_consumed_total",
    help: "Total number of messages consumed",
    labelNames: ["event_type", "outcome"] as const,
    registers: [registry]
  });

  const messageProcessingDurationSeconds = new Histogram({
    name: "ecommerce_message_processing_duration_seconds",
    help: "Duration of message processing in seconds",
    labelNames: ["event_type", "outcome"] as const,
    buckets: [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10, 30],
    registers: [registry]
  });

  return {
    registry,
    httpRequestsTotal,
    httpRequestDurationSeconds,
    httpRequestsInFlight,
    dependencyHealth,
    messagesPublishedTotal,
    messagesConsumedTotal,
    messageProcessingDurationSeconds
  };
}

export type ServiceMetrics = ReturnType<typeof createMetrics>;
```

Why these metrics?

- `http_requests_total` measures throughput and response outcomes.
- `http_request_duration_seconds` enables latency percentiles using histogram buckets.
- `http_requests_in_flight` shows concurrent request load.
- `dependency_up` gives a basic view of dependency health.
- Message counters and duration histograms help diagnose event-processing failures and slow consumers.
- Default process metrics expose runtime information such as Node.js memory and event-loop behavior where supported by `prom-client`.

Don't add user IDs, order IDs, request IDs, raw URLs, or arbitrary error messages as metric labels. Those values create excessive time series and can expose sensitive data.

## 3. Instrument every Express service

The middleware should record each completed request and measure its duration. Crucially, it must use the route template (`/orders/:orderId`), not the concrete path (`/orders/928173`).

### `packages/observability/src/http-metrics.ts`

```
import type { Request, RequestHandler } from "express";
import type { ServiceMetrics } from "./metrics.js";

const ALLOWED_METHODS = new Set([
  "GET",
  "POST",
  "PUT",
  "PATCH",
  "DELETE",
  "OPTIONS",
  "HEAD"
]);

function getMethod(method: string): string {
  return ALLOWED_METHODS.has(method) ? method : "OTHER";
}

function getRouteLabel(request: Request): string {
  const routePath = request.route?.path;

  if (typeof routePath === "string") {
    // Express route templates preserve parameters, e.g. /orders/:orderId.
    return `${request.baseUrl}${routePath}` || "/";
  }

  // Never use request.originalUrl here: it may contain IDs or sensitive data.
  return "unmatched";
}

export interface HttpMetricsMiddlewareOptions {
  metrics: ServiceMetrics;
  ignoredPaths?: string[];
}

export function createHttpMetricsMiddleware(
  options: HttpMetricsMiddlewareOptions
): RequestHandler {
  const { metrics, ignoredPaths = ["/metrics", "/health/live", "/health/ready"] } = options;

  return (request, response, next) => {
    if (ignoredPaths.includes(request.path)) {
      next();
      return;
    }

    const method = getMethod(request.method);
    const startedAt = process.hrtime.bigint();

    metrics.httpRequestsInFlight.inc({ method });

    let recorded = false;

    const recordRequest = () => {
      if (recorded) return;
      recorded = true;

      const elapsedSeconds =
        Number(process.hrtime.bigint() - startedAt) / 1_000_000_000;

      const labels = {
        method,
        route: getRouteLabel(request),
        status_code: String(response.statusCode)
      };

      metrics.httpRequestsTotal.inc(labels);
      metrics.httpRequestDurationSeconds.observe(labels, elapsedSeconds);
      metrics.httpRequestsInFlight.dec({ method });
    };

    response.once("finish", recordRequest);

    // "close" also covers a client disconnect before "finish".
    response.once("close", recordRequest);

    next();
  };
}
```

### Important middleware ordering

Register the metrics middleware before application routes, so it can observe successful responses, 4xx errors, and 5xx errors.

```
import express from "express";
import { createMetrics } from "@ecommerce/observability";
import { createHttpMetricsMiddleware } from "@ecommerce/observability/http";

const app = express();

const metrics = createMetrics({
  serviceName: "order-service"
});

app.use(createHttpMetricsMiddleware({ metrics }));

// Then register JSON parsing, request context, application routes,
// not-found handling, and the final error handler.
```

The code above illustrates placement; preserve your actual error-handling and request-context order. The `close` event handler is idempotent, so a response that emits both `finish` and `close` is counted only once.

## 4. Expose the Prometheus endpoint

### `packages/observability/src/metrics-endpoint.ts`

```
import type { RequestHandler } from "express";
import type { ServiceMetrics } from "./metrics.js";

export function createMetricsEndpoint(
  metrics: ServiceMetrics
): RequestHandler {
  return async (_request, response, next) => {
    try {
      response.setHeader(
        "Content-Type",
        metrics.registry.contentType
      );

      response.status(200).send(await metrics.registry.metrics());
    } catch (error) {
      next(error);
    }
  };
}
```

Add this export to `packages/observability/src/index.ts`:

```
export { createMetrics } from "./metrics.js";
export type { MetricsOptions, ServiceMetrics } from "./metrics.js";

export { createHttpMetricsMiddleware } from "./http-metrics.js";
export type {
  HttpMetricsMiddlewareOptions
} from "./http-metrics.js";

export { createMetricsEndpoint } from "./metrics-endpoint.js";
```

Mount the endpoint after your metrics registry is created:

```

```

Security requirement: `/metrics` is an internal operational endpoint. Do not expose it publicly without access controls. Prefer keeping it on an internal network and configuring Prometheus to scrape it there.

## 5. Add messaging instrumentation

Your event-driven architecture needs visibility into successful publications, failed publications, and message-handler outcomes. The shared package should provide instrumentation helpers without taking ownership of RabbitMQ acknowledgements or retry behavior.

### `packages/observability/src/messaging-metrics.ts`

```
import type { ServiceMetrics } from "./metrics.js";

export interface MessageMetricLabels {
  eventType: string;
  outcome: "success" | "failure";
}

export function recordMessagePublished(
  metrics: ServiceMetrics,
  input: {
    exchange: string;
    eventType: string;
    outcome: "success" | "failure";
  }
): void {
  metrics.messagesPublishedTotal.inc({
    exchange: input.exchange,
    event_type: input.eventType,
    outcome: input.outcome
  });
}

export async function observeMessageProcessing<T>(
  metrics: ServiceMetrics,
  input: MessageMetricLabels,
  handler: () => Promise<T>
): Promise<T> {
  const startedAt = process.hrtime.bigint();

  try {
    const result = await handler();

    metrics.messagesConsumedTotal.inc({
      event_type: input.eventType,
      outcome: "success"
    });

    return result;
  } catch (error) {
    metrics.messagesConsumedTotal.inc({
      event_type: input.eventType,
      outcome: "failure"
    });

    throw error;
  } finally {
    const durationSeconds =
      Number(process.hrtime.bigint() - startedAt) / 1_000_000_000;

    metrics.messageProcessingDurationSeconds.observe(
      {
        event_type: input.eventType,
        outcome: input.outcome
      },
      durationSeconds
    );
  }
}
```

Export it from `src/index.ts`:

```
export {
  recordMessagePublished,
  observeMessageProcessing
} from "./messaging-metrics.js";

export type {
  MessageMetricLabels
} from "./messaging-metrics.js";
```

### A correction before integrating this helper

The implementation above should be tightened before use: its `input.outcome` is supplied by the caller, so it can disagree with the handler result. Replace `observeMessageProcessing` with this version, which derives the outcome itself:

```
export async function observeMessageProcessing<T>(
  metrics: ServiceMetrics,
  input: { eventType: string },
  handler: () => Promise<T>
): Promise<T> {
  const startedAt = process.hrtime.bigint();
  let outcome: "success" | "failure" = "success";

  try {
    const result = await handler();

    metrics.messagesConsumedTotal.inc({
      event_type: input.eventType,
      outcome
    });

    return result;
  } catch (error) {
    outcome = "failure";

    metrics.messagesConsumedTotal.inc({
      event_type: input.eventType,
      outcome
    });

    throw error;
  } finally {
    metrics.messageProcessingDurationSeconds.observe(
      {
        event_type: input.eventType,
        outcome
      },
      Number(process.hrtime.bigint() - startedAt) / 1_000_000_000
    );
  }
}
```

Use bounded, predefined event names such as `order.created` or `payment.succeeded`. Never use a message's arbitrary payload fields as labels. Also, incrementing a publish counter should reflect a confirmed publication, not merely an attempted send.

### `packages/observability/tests/http-metrics.test.ts`

```
import express from "express";
import { createServer } from "node:http";
import { once } from "node:events";
import { afterEach, describe, expect, it } from "vitest";
import { createMetrics } from "../src/metrics.js";
import { createHttpMetricsMiddleware } from "../src/http-metrics.js";

describe("HTTP metrics middleware", () => {
  const servers: ReturnType<typeof createServer>[] = [];

  afterEach(async () => {
    await Promise.all(
      servers.splice(0).map((server) =>
        new Promise<void>((resolve) => {
          server.close(() => resolve());
          server.closeAllConnections?.();
        })
      )
    );
  });

  it("records route template, status and request count", async () => {
    const metrics = createMetrics({
      serviceName: "order-service",
      collectDefaultProcessMetrics: false
    });

    const app = express();

    app.use(createHttpMetricsMiddleware({ metrics }));

    app.get("/orders/:orderId", (_req, res) => {
      res.status(200).json({ ok: true });
    });

    const server = createServer(app);
    servers.push(server);
    server.listen(0, "127.0.0.1");
    await once(server, "listening");

    const address = server.address();

    if (!address || typeof address === "string") {
      throw new Error("Expected TCP address");
    }

    const response = await fetch(
      `http://127.0.0.1:${address.port}/orders/12345`
    );

    expect(response.status).toBe(200);

    // The response "finish" event records metrics asynchronously relative
    // to the client receiving its response, so allow the event loop to run.
    await new Promise((resolve) => setImmediate(resolve));

    const output = await metrics.registry.metrics();

    expect(output).toContain('route="/orders/:orderId"');
    expect(output).toContain('status_code="200"');
    expect(output).not.toContain('route="/orders/12345"');
  });

  it("does not count ignored health endpoints", async () => {
    const metrics = createMetrics({
      serviceName: "order-service",
      collectDefaultProcessMetrics: false
    });

    const app = express();
    app.use(createHttpMetricsMiddleware({ metrics }));
    app.get("/health/live", (_req, res) => res.sendStatus(200));

    const server = createServer(app);
    servers.push(server);
    server.listen(0, "127.0.0.1");
    await once(server, "listening");

    const address = server.address();

    if (!address || typeof address === "string") {
      throw new Error("Expected TCP address");
    }

    await fetch(`http://127.0.0.1:${address.port}/health/live`);

    const output = await metrics.registry.metrics();

    expect(output).not.toContain("ecommerce_http_requests_total");
  });
});
```

## 9. Add dependency health instrumentation

The `dependency_up` gauge is defined, but services need to update it when checking their dependencies. Add this helper to `packages/observability/src/metrics.ts` or place it in a separate `dependency-metrics.ts` module:

```
import type { ServiceMetrics } from "./metrics.js";

export function recordDependencyHealth(
  metrics: ServiceMetrics,
  dependency: "postgres" | "mongodb" | "redis" | "rabbitmq",
  isHealthy: boolean
): void {
  metrics.dependencyHealth.set(
    { dependency },
    isHealthy ? 1 : 0
  );
}
```

If you use a separate module, export the helper from `src/index.ts`.

Call it from your health-check scheduler or dependency health adapter, for example:

```
recordDependencyHealth(metrics, "postgres", true);
```

Only report `true` after an actual successful health check. Don't hardcode a healthy state at startup. For a production implementation, update these gauges periodically and on meaningful connection-state changes, and initialize known dependencies to `0` until their first successful check.

## 11. Final implementation review

Before considering Phase 1.9 complete, address these details:

- Fix the ignored-path test: Prometheus output can contain a metric's `HELP` and `TYPE` metadata even when it has no samples. Instead of asserting the metric name is absent, assert that no sample line exists for the ignored request.
- Use only the corrected messaging helper: The second `observeMessageProcessing` implementation replaces the first. Keep just one definition in the file.
- Bound readiness checks: A metrics package should not make health endpoints hang if PostgreSQL or RabbitMQ becomes unresponsive.
- Instrument real outcomes: Publisher metrics must reflect broker-confirmed outcomes, and consumer metrics should distinguish processing failures from successful retries or dead-lettering.
- Protect observability endpoints: Keep `/metrics` internal, avoid secrets in logs, and never use unbounded label values.
