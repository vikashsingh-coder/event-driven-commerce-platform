# Phase 1.1 — Shared Configuration Package

We'll implement the first real package in your Event-Driven E-Commerce Backend monorepo: a type-safe, validated configuration system shared across all six microservices.

The goal is to eliminate scattered `process.env` access, catch missing or invalid configuration before a service starts, and make each service explicitly declare which infrastructure and secrets it needs.

## 1. What we're building

Environment variables

Local `.env` · CI variables · Production secret injection

Zod validation

Required fields · Type checks · Safe defaults · Constraints

Typed service configuration

No raw environment-variable access in business code

Auth

Product

Order

The same package will also support Payment, Notification, and Analytics.

Implementation decisions

- TypeScript with Zod for runtime validation and inferred types.
- One shared package at `packages/config`.
- Separate schemas for each service, so a service doesn't need unrelated secrets.
- Fail-fast validation with useful, redacted error messages.
- No production secrets in source control.
- Unit tests for valid, invalid, and service-specific configurations.

## 4. Define the common schema

### `packages/config/src/schemas/common.schema.ts`

Every service shares the same basic runtime environment and logging configuration.

```

import { z } from "zod";

export const nodeEnvironmentSchema = z.enum([
  "development",
  "test",
  "production",
]);

export const logLevelSchema = z.enum([
  "debug",
  "info",
  "warn",
  "error",
]);

export const commonEnvSchema = z.object({
  NODE_ENV: nodeEnvironmentSchema.default("development"),

  LOG_LEVEL: logLevelSchema.default("info"),
});

export type CommonEnv = z.infer<typeof commonEnvSchema>;

```

Why not put every variable into this schema?

Because the Auth Service should not need payment-provider secrets, and the Notification Service should not need payment database credentials just because both import the same package.

## 6. Build the configuration loader

This is the core of the package. It combines common validation with a service-specific schema, converts the port to a number, and returns a typed configuration object.

### `packages/config/src/errors.ts`

```

export interface ConfigValidationIssue {
  field: string;
  message: string;
}

export class ConfigValidationError extends Error {
  constructor(issues: ConfigValidationIssue[]) {
    const details = issues
      .map(({ field, message }) => `  - ${field}: ${message}`)
      .join("\n");

    super(`Configuration validation failed:\n${details}`);

    this.name = "ConfigValidationError";
  }
}

```

We deliberately display the field and validation message—not the supplied value. This reduces the risk of exposing credentials in startup logs.

### `packages/config/src/create-config.ts`

```

import { z } from "zod";

import { commonEnvSchema } from "./schemas/common.schema.js";
import { ConfigValidationError } from "./errors.js";

const portSchema = z.coerce
  .number()
  .int()
  .min(1)
  .max(65535);

type Environment = Record<string, string | undefined>;

interface CreateConfigOptions<T extends z.ZodRawShape> {
  serviceName: string;
  defaultPort: number;
  schema: z.ZodObject<T>;
  env?: Environment;
}

export function createConfig<T extends z.ZodRawShape>({
  serviceName,
  defaultPort,
  schema,
  env = process.env,
}: CreateConfigOptions<T>) {
  const combinedSchema = commonEnvSchema.merge(schema);

  const parsed = combinedSchema.safeParse(env);

  const port = portSchema.safeParse(
    env.PORT ?? defaultPort,
  );

  const issues = [
    ...(parsed.success
      ? []
      : parsed.error.issues.map((issue) => ({
          field: issue.path.join(".") || "environment",
          message: issue.message,
        }))),

    ...(port.success
      ? []
      : [
          {
            field: "PORT",
            message: "Must be an integer between 1 and 65535",
          },
        ]),
  ];

  if (issues.length > 0 || !parsed.success || !port.success) {
    throw new ConfigValidationError(issues);
  }

  return Object.freeze({
    env: parsed.data.NODE_ENV,
    logLevel: parsed.data.LOG_LEVEL,

    service: Object.freeze({
      name: serviceName,
      port: port.data,
    }),

    dependencies: Object.freeze({
      ...parsed.data,
    }),
  });
}

```

### How this works

1. `commonEnvSchema` validates `NODE_ENV` and `LOG_LEVEL`.
2. The supplied service schema validates that service's dependencies.
3. `PORT` is converted to a number and checked against valid TCP port bounds.
4. All validation failures are reported together.
5. Invalid configuration throws an error, preventing startup.
6. The returned configuration is frozen to discourage accidental mutation.

One important distinction: `Object.freeze` is shallow. We freeze the top-level result and its immediate objects, which is sufficient for these flat configuration fields. For nested configuration added later, we should freeze those objects too or use an immutable configuration type.

## 7. Use the package in a service

For example, in the Order Service:

### `apps/order-service/src/config/index.ts`

```

import {
  createConfig,
  orderEnvSchema,
} from "@ecommerce/config";

export const config = createConfig({
  serviceName: "order-service",
  defaultPort: 3003,
  schema: orderEnvSchema,
});

export type OrderServiceConfig = typeof config;

```

Application code can now use:

```
import { config } from "./config/index.js";

console.log(config.service.name);
console.log(config.service.port);
console.log(config.env);
console.log(config.dependencies.DATABASE_URL);
console.log(config.dependencies.RABBITMQ_URL);
```

For production code, don't log secret values. The last two lines illustrate access, not a recommendation to print connection strings.

Because the returned object is inferred from Zod, TypeScript understands that `PORT` is a number and the environment is one of the supported values.

### Configure the other services

Use the same pattern with the appropriate schema and default port:

| Service      | Default port | Schema                  |
| ------------ | ------------ | ----------------------- |
| Auth         | 3001         | `authEnvSchema`         |
| Product      | 3002         | `productEnvSchema`      |
| Order        | 3003         | `orderEnvSchema`        |
| Payment      | 3004         | `paymentEnvSchema`      |
| Notification | 3005         | `notificationEnvSchema` |
| Analytics    | 3006         | `analyticsEnvSchema`    |

The `PORT` environment variable can override the default for local development or deployment.

```
JWT_ACCESS_EXPIRES_IN=15m
JWT_REFRESH_EXPIRES_IN=7d

# Razorpay — use test credentials locally
RAZORPAY_KEY_ID=replace_me
RAZORPAY_KEY_SECRET=replace_me
RAZORPAY_WEBHOOK_SECRET=replace_me

# Stripe — use test credentials locally
STRIPE_SECRET_KEY=replace_me
STRIPE_WEBHOOK_SECRET=replace_me

```

These are placeholders, not working credentials. Generate distinct JWT secrets for local development; never use this template as a production secrets file.

Generate a local secret using:

```
openssl rand -base64 32
```

Important: The shared configuration package does not automatically load `.env`. Load it through your service's development runner or use Node.js environment-file support. This keeps configuration validation separate from the mechanism that supplies environment variables.

## 9. Add automated tests

We need to verify not just the happy path, but also failure behavior.

### `packages/config/tests/create-config.test.ts`

```

import { describe, expect, it } from "vitest";

import {
  createConfig,
  ConfigValidationError,
  orderEnvSchema,
} from "../src/index.js";

const validEnv = {
  NODE_ENV: "test",
  LOG_LEVEL: "info",
  DATABASE_URL: "postgresql://user:pass@localhost:5432/orders",
  REDIS_URL: "redis://localhost:6379",
  RABBITMQ_URL: "amqp://user:pass@localhost:5672",
};

describe("createConfig", () => {
  it("returns validated configuration", () => {
    const config = createConfig({
      serviceName: "order-service",
      defaultPort: 3003,
      schema: orderEnvSchema,
      env: validEnv,
    });

    expect(config.service.name).toBe("order-service");
    expect(config.service.port).toBe(3003);
    expect(config.env).toBe("test");
    expect(config.dependencies.DATABASE_URL).toBe(
      validEnv.DATABASE_URL,
    );
  });

  it("converts a valid PORT string to a number", () => {
    const config = createConfig({
      serviceName: "order-service",
      defaultPort: 3003,
      schema: orderEnvSchema,
      env: {
        ...validEnv,
        PORT: "3010",
      },
    });

    expect(config.service.port).toBe(3010);
    expect(typeof config.service.port).toBe("number");
  });

  it("rejects an invalid PORT", () => {
    expect(() =>
      createConfig({
        serviceName: "order-service",
        defaultPort: 3003,
        schema: orderEnvSchema,
        env: {
          ...validEnv,
          PORT: "70000",
        },
      }),
    ).toThrow(ConfigValidationError);
  });

  it("rejects a missing required database URL", () => {
    const { DATABASE_URL: _ignored, ...envWithoutDatabase } =
      validEnv;

    expect(() =>
      createConfig({
        serviceName: "order-service",
        defaultPort: 3003,
        schema: orderEnvSchema,
        env: envWithoutDatabase,
      }),
    ).toThrow(ConfigValidationError);
  });

  it("rejects an invalid runtime environment", () => {
    expect(() =>
      createConfig({
        serviceName: "order-service",
        defaultPort: 3003,
        schema: orderEnvSchema,
        env: {
          ...validEnv,
          NODE_ENV: "staging",
        },
      }),
    ).toThrow(ConfigValidationError);
  });

  it("uses common defaults when optional fields are absent", () => {
    const config = createConfig({
      serviceName: "order-service",
      defaultPort: 3003,
      schema: orderEnvSchema,
      env: {
        DATABASE_URL: validEnv.DATABASE_URL,
        REDIS_URL: validEnv.REDIS_URL,
        RABBITMQ_URL: validEnv.RABBITMQ_URL,
      },
    });

    expect(config.env).toBe("development");
    expect(config.logLevel).toBe("info");
  });

  it("does not expose secret values in validation errors", () => {
    const secret = "private-database-password";

    try {
      createConfig({
        serviceName: "order-service",
        defaultPort: 3003,
        schema: orderEnvSchema,
        env: {
          NODE_ENV: "invalid",
          DATABASE_URL: secret,
          REDIS_URL: validEnv.REDIS_URL,
          RABBITMQ_URL: validEnv.RABBITMQ_URL,
        },
      });

      throw new Error("Expected configuration validation to fail");
    } catch (error) {
      expect(error).toBeInstanceOf(ConfigValidationError);
      expect((error as Error).message).not.toContain(secret);
    }
  });
});

```

The last test checks that invalid configuration doesn't leak a supplied value into the error message.
