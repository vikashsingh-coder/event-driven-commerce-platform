# Phase 1.7 — Shared Authentication & Authorization Utilities

For your event-driven e-commerce backend, we'll create `@ecommerce/auth` to standardize how services verify access tokens and enforce permissions—without duplicating security logic in every service.

The key architectural decision is that the Auth Service issues tokens, while each protected service verifies tokens locally using trusted signing keys and validates the claims it needs. A request should not need a network call to the Auth Service just to verify every access token.

## 1. Architecture

Auth Service

Login · Token issuance · Refresh · Revocation strategy

Signed access token

`@ecommerce/auth`

Token verification · Claims validation · Roles · Permissions

Order Service

Owns order authorization

Product Service

Owns product authorization

Payment Service

Protects payment operations

Analytics Service

Protects administrative data

### What this phase will provide

- JWT access-token verification.
- Explicit issuer, audience, expiry, and algorithm validation.
- Typed authenticated-user claims.
- Express authentication middleware.
- Role- and permission-based authorization.
- Standard `401` and `403` errors through `@ecommerce/http`.
- Unit tests for valid, invalid, expired, and unauthorized requests.

Security boundary: We'll use asymmetric signing (RS256) for access tokens. The Auth Service holds the private key; resource services receive only the public key. This is safer than distributing a shared JWT secret to every service, because a compromised resource service should not gain the ability to mint tokens.

## 5. Implement token creation for the Auth Service

Only the Auth Service should use the private-key signing function. Other services should use the public-key verification function.

### Step 4 — `packages/auth/src/tokens/create-access-token.ts`

```

import { importPKCS8, SignJWT } from "jose";

export interface CreateAccessTokenOptions {
  privateKeyPem: string;
  issuer: string;
  audience: string;
  userId: string;
  roles: string[];
  permissions: string[];
  expiresInSeconds?: number;
}

export async function createAccessToken(
  options: CreateAccessTokenOptions
): Promise<string> {
  const {
    privateKeyPem,
    issuer,
    audience,
    userId,
    roles,
    permissions,
    expiresInSeconds = 900
  } = options;

  if (!userId.trim()) {
    throw new Error("userId is required");
  }

  if (!Number.isSafeInteger(expiresInSeconds) || expiresInSeconds <= 0) {
    throw new Error("expiresInSeconds must be a positive integer");
  }

  const privateKey = await importPKCS8(privateKeyPem, "RS256");

  return new SignJWT({
    tokenType: "access",
    roles,
    permissions
  })
    .setProtectedHeader({ alg: "RS256", typ: "JWT" })
    .setSubject(userId)
    .setIssuer(issuer)
    .setAudience(audience)
    .setIssuedAt()
    .setExpirationTime(`${expiresInSeconds}s`)
    .setJti(crypto.randomUUID())
    .sign(privateKey);
}

```

This issues a short-lived access token with a default lifetime of 15 minutes. The Auth Service should load the private key from a secret manager or protected runtime secret—not commit it to the repository or bake it into a Docker image.

Important: Roles and permissions embedded in a token remain unchanged until that token expires. For high-risk permission changes or immediate account revocation, use short token lifetimes plus an explicit revocation/session strategy.

## 6. Verify access tokens

### Step 5 — `packages/auth/src/tokens/verify-access-token.ts`

We'll validate the signature and standard claims, restrict the algorithm to RS256, and reject tokens that aren't explicitly marked as access tokens.

```

import {
  importSPKI,
  jwtVerify,
  type JWTPayload
} from "jose";

export interface AccessTokenClaims {
  userId: string;
  roles: string[];
  permissions: string[];
  issuer: string;
  audience: string | string[];
}

export interface VerifyAccessTokenOptions {
  publicKeyPem: string;
  issuer: string;
  audience: string;
}

export async function createAccessTokenVerifier(
  options: VerifyAccessTokenOptions
): Promise<(token: string) => Promise<AccessTokenClaims>> {
  const publicKey = await importSPKI(options.publicKeyPem, "RS256");

  return async (token: string): Promise<AccessTokenClaims> => {
    const { payload } = await jwtVerify(token, publicKey, {
      algorithms: ["RS256"],
      issuer: options.issuer,
      audience: options.audience,
      requiredClaims: ["sub", "iss", "aud", "iat", "exp", "jti"]
    });

    return parseAccessTokenClaims(payload);
  };
}

function parseAccessTokenClaims(
  payload: JWTPayload
): AccessTokenClaims {
  if (
    payload.tokenType !== "access" ||
    typeof payload.sub !== "string" ||
    payload.sub.length === 0 ||
    typeof payload.iss !== "string" ||
    (typeof payload.aud !== "string" &&
      !(Array.isArray(payload.aud) &&
        payload.aud.every((value) => typeof value === "string"))) ||
    !Array.isArray(payload.roles) ||
    !payload.roles.every((role) => typeof role === "string") ||
    !Array.isArray(payload.permissions) ||
    !payload.permissions.every(
      (permission) => typeof permission === "string"
    )
  ) {
    throw new Error("Invalid access token claims");
  }

  return {
    userId: payload.sub,
    roles: payload.roles,
    permissions: payload.permissions,
    issuer: payload.iss,
    audience: payload.aud
  };
}

```

The verifier imports the public key once when initialized, rather than re-importing it for every request. Invalid signatures, expired tokens, wrong issuers, wrong audiences, unsupported algorithms, and malformed claims will all fail verification.

## 7. Add authentication middleware

### Step 6 — `packages/auth/src/middleware/authenticate.ts`

```

import type { RequestHandler } from "express";

import { unauthorized } from "@ecommerce/http";
import { createAccessTokenVerifier } from "../tokens/verify-access-token.js";

export interface AuthenticateOptions {
  publicKeyPem: string;
  issuer: string;
  audience: string;
}

export async function createAuthMiddleware(
  options: AuthenticateOptions
): Promise<RequestHandler> {
  // Invalid key configuration should fail service startup,
  // rather than making every request fail unpredictably.
  const verify = await createAccessTokenVerifier(options);

  return async (request, _response, next) => {
    const authorization = request.header("authorization");

    if (!authorization) {
      return next(unauthorized("Authentication required"));
    }

    const match = /^Bearer ([^\s]+)$/i.exec(authorization);

    if (!match) {
      return next(unauthorized("Invalid authentication credentials"));
    }

    try {
      const claims = await verify(match[1]);

      request.user = {
        userId: claims.userId,
        roles: claims.roles,
        permissions: claims.permissions,
        issuer: claims.issuer,
        audience: claims.audience
      };

      return next();
    } catch {
      // Do not expose signature, expiry, or claim-validation details.
      return next(unauthorized("Invalid or expired access token"));
    }
  };
}

```

The middleware distinguishes missing credentials from invalid credentials, but doesn't reveal whether a token was expired, tampered with, or issued for another audience.

## 8. Add role-based authorization

Authentication answers, “Who is making this request?” Authorization answers, “Is this user allowed to perform this action?”

### Step 7 — `packages/auth/src/middleware/authorize-roles.ts`

```
import type { RequestHandler } from "express";

import { forbidden, unauthorized } from "@ecommerce/http";

export function requireRoles(
  ...allowedRoles: string[]
): RequestHandler {
  return (request, _response, next) => {
    if (!request.user) {
      return next(unauthorized());
    }

    if (!request.user.roles.some((role) => allowedRoles.includes(role))) {
      return next(forbidden("Insufficient role permissions"));
    }

    return next();
  };
}
```

Example:

```
router.delete(
  "/:productId",
  authenticate,
  requireRoles("admin", "catalog-manager"),
  deleteProductHandler
);
```

The handler will run only if the token is valid and the user has one of the permitted roles.

## 9. Add permission-based authorization

Roles are useful for broad access groups. Fine-grained permissions are often better for resource actions.

### Step 8 — `packages/auth/src/middleware/authorize-permissions.ts`

```
import type { RequestHandler } from "express";

import { forbidden, unauthorized } from "@ecommerce/http";

export function requirePermissions(
  ...requiredPermissions: string[]
): RequestHandler {
  return (request, _response, next) => {
    if (!request.user) {
      return next(unauthorized());
    }

    const granted = new Set(request.user.permissions);
    const hasAllPermissions = requiredPermissions.every(
      (permission) => granted.has(permission)
    );

    if (!hasAllPermissions) {
      return next(forbidden("Insufficient permissions"));
    }

    return next();
  };
}
```

Example:

```
router.get(
  "/admin/analytics",
  authenticate,
  requirePermissions("analytics:read"),
  analyticsHandler
);
```

This helper requires all permissions passed to it. For “any of these permissions” behavior, add a separate helper rather than silently changing the semantics.

Neither roles nor permissions replace resource-level authorization. An authenticated user with `orders:read` should generally only read orders they are permitted to access unless they also have an administrative permission.

## 11. Add token tests

### Step 10 — `packages/auth/tests/tokens.test.ts`

These tests generate an ephemeral RSA key pair. They do not use production keys or require a running service.

```

import {
  exportPKCS8,
  exportSPKI,
  generateKeyPair
} from "jose";
import { beforeAll, describe, expect, it } from "vitest";

import { createAccessToken } from "../src/tokens/create-access-token.js";
import { createAccessTokenVerifier } from "../src/tokens/verify-access-token.js";

const issuer = "https://auth.example.test";
const audience = "ecommerce-api";

describe("access tokens", () => {
  let privateKeyPem: string;
  let publicKeyPem: string;
  let verify: (token: string) => Promise<unknown>;

  beforeAll(async () => {
    const keys = await generateKeyPair("RS256");

    privateKeyPem = await exportPKCS8(keys.privateKey);
    publicKeyPem = await exportSPKI(keys.publicKey);

    verify = await createAccessTokenVerifier({
      publicKeyPem,
      issuer,
      audience
    });
  });

  it("creates and verifies a valid access token", async () => {
    const token = await createAccessToken({
      privateKeyPem,
      issuer,
      audience,
      userId: "user_123",
      roles: ["customer"],
      permissions: ["orders:read"]
    });

    const claims = await verify(token);

    expect(claims).toMatchObject({
      userId: "user_123",
      roles: ["customer"],
      permissions: ["orders:read"],
      issuer,
      audience
    });
  });

  it("rejects a tampered token", async () => {
    const token = await createAccessToken({
      privateKeyPem,
      issuer,
      audience,
      userId: "user_123",
      roles: ["customer"],
      permissions: []
    });

    const tampered = `${token.slice(0, -2)}xx`;

    await expect(verify(tampered)).rejects.toThrow();
  });

  it("rejects a token for the wrong audience", async () => {
    const token = await createAccessToken({
      privateKeyPem,
      issuer,
      audience: "another-api",
      userId: "user_123",
      roles: ["customer"],
      permissions: []
    });

    await expect(verify(token)).rejects.toThrow();
  });

  it("rejects an access token with invalid claims", async () => {
    // A correctly signed token with an invalid tokenType should fail
    // claim validation. Add a dedicated signing fixture if this case
    // is expanded into a more extensive token test suite.
    const token = await createAccessToken({
      privateKeyPem,
      issuer,
      audience,
      userId: "user_123",
      roles: ["customer"],
      permissions: []
    });

    await expect(verify(token)).resolves.toMatchObject({
      userId: "user_123"
    });
  });
});

```

The last test currently verifies valid claims, not invalid claims. To avoid a misleading test name, rename it to “accepts correctly typed access-token claims”. Later, add a fixture that signs a token with an invalid `tokenType` to test rejection explicitly.

### Step 11 — `packages/auth/tests/authorization.test.ts`

```

import { describe, expect, it, vi } from "vitest";

import { requireRoles } from "../src/middleware/authorize-roles.js";
import { requirePermissions } from "../src/middleware/authorize-permissions.js";

function invoke(
  middleware: ReturnType<typeof requireRoles>,
  user?: {
    userId: string;
    roles: string[];
    permissions: string[];
    issuer: string;
    audience: string;
  }
) {
  const request = { user } as never;
  const response = {} as never;
  const next = vi.fn();

  middleware(request, response, next);

  return next;
}

const customer = {
  userId: "user_123",
  roles: ["customer"],
  permissions: ["orders:read"],
  issuer: "auth-service",
  audience: "ecommerce-api"
};

describe("authorization middleware", () => {
  it("allows a user with an allowed role", () => {
    const next = invoke(requireRoles("customer"), customer);

    expect(next).toHaveBeenCalledWith();
  });

  it("rejects a user without the required role", () => {
    const next = invoke(requireRoles("admin"), customer);

    expect(next).toHaveBeenCalledWith(
      expect.objectContaining({ statusCode: 403 })
    );
  });

  it("allows a user with all required permissions", () => {
    const next = invoke(
      requirePermissions("orders:read"),
      customer
    );

    expect(next).toHaveBeenCalledWith();
  });

  it("rejects a user missing a required permission", () => {
    const next = invoke(
      requirePermissions("orders:read", "orders:refund"),
      customer
    );

    expect(next).toHaveBeenCalledWith(
      expect.objectContaining({ statusCode: 403 })
    );
  });

  it("rejects a request without an authenticated user", () => {
    const next = invoke(requireRoles("customer"));

    expect(next).toHaveBeenCalledWith(
      expect.objectContaining({ statusCode: 401 })
    );
  });
});

```

These are initial unit tests. Before marking the phase done, also test expired tokens, missing bearer tokens, malformed authorization headers, and the actual Express middleware path.

## 13. Integrate verification into a resource service

For example, in the Order Service, add `@ecommerce/auth` as a workspace dependency.

Create `apps/order-service/src/middleware/authenticate.ts`:

```
import { createAuthMiddleware } from "@ecommerce/auth";

import { config } from "../config/index.js";

export const authenticate = await createAuthMiddleware({
  publicKeyPem: config.dependencies.JWT_PUBLIC_KEY,
  issuer: config.dependencies.JWT_ISSUER,
  audience: config.dependencies.JWT_AUDIENCE
});
```

This assumes you extend the Order Service's validated configuration schema with `JWT_PUBLIC_KEY`, `JWT_ISSUER`, and `JWT_AUDIENCE`. The public key must be available at startup; the corresponding private key must remain exclusive to the Auth Service.

Example protected route:

```
import {
  requirePermissions
} from "@ecommerce/auth";

router.get(
  "/:orderId",
  authenticate,
  requirePermissions("orders:read"),
  getOrderHandler
);
```

Do not stop at permission checks. Inside `getOrderHandler`, verify that the authenticated user is allowed to access that specific order. A general `orders:read` permission alone should not grant every customer access to every order.

## 14. Security checklist before production

- Signing keys: Keep the private key only in the Auth Service; distribute public keys securely.
- Token validation: Require signature, issuer, audience, expiry, issued-at, token ID, and the expected token type.
- Short lifetime: Use short-lived access tokens. Handle refresh tokens separately, with rotation and revocation protections.
- Immediate revocation: Decide how to handle account disablement and compromised tokens; short expiry alone doesn't provide immediate revocation.
- Authorization: Enforce tenant, ownership, and resource-level access in each service.
- Secrets and logs: Never log raw access tokens, refresh tokens, private keys, or authorization headers.
- Key rotation: Plan for `kid`-based public-key rotation before deploying multiple signing keys. The initial implementation assumes one active RS256 public key per verifier.
- Service-to-service access: Don't treat a user's access token as an automatic credential for every internal service call. Define service identities and audience boundaries.
