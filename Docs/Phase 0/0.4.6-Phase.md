# Phase 0.4.6 — RabbitMQ Infrastructure

Our goal is not merely to "install RabbitMQ."

We want a production-style foundation supporting:

- Event-driven communication
- Publisher confirms
- Durable exchanges/queues
- Persistent messages
- Dead-letter queues
- Retry queues
- TTL-based retries
- Manual acknowledgements
- Consumer prefetch
- Idempotent consumers
- Routing keys
- Correlation IDs
- Trace IDs
- Graceful shutdown
- Health checks

# 2. Why RabbitMQ?

Consider order creation.

Without messaging:

```text
Order Service
     │
     ├── Inventory Service
     ├── Payment Service
     ├── Notification Service
     └── Analytics Service
```

Order Service becomes tightly coupled to everything.

Instead:

```text
Order Service
      │
      ▼
Order Created Event
      │
      ▼
RabbitMQ
      │
      ├───────────────┐
      ▼               ▼
Inventory         Payment
      │
      ├───────────────┐
      ▼               ▼
Notification      Analytics
```

The Order Service doesn't need to know exactly how every downstream service works.

# 16. Queue Architecture

We'll create queues based on **consumer responsibility**, not merely event type.

For example:

```text
inventory-service.events
payment-service.events
notification-service.events
analytics-service.events
```

This is important.

We don't want:

```text
order-created.queue
```

for every consumer.

Instead:

```text
Order Created
     │
     ▼
RabbitMQ Exchange
     │
     ├── inventory-service.events
     ├── payment-service.events
     ├── notification-service.events
     └── analytics-service.events
```

Each service receives its own copy.

---

# 17. Why Separate Queues?

RabbitMQ queues provide independent consumption.

Suppose:

```text
Inventory Service
```

is slow.

We don't want that to prevent:

```text
Analytics Service
```

from consuming the event.

With separate queues:

```text
                    order.created
                         │
                         ▼
                  ecommerce.events
                   │      │      │
                   ▼      ▼      ▼
              inventory payment analytics
```

Each consumer progresses independently.

# 22. Standard Event Envelope

Every message in our system should follow the same structure.

```typescript
interface EventEnvelope<T> {
  eventId: string;

  eventType: string;

  eventVersion: number;

  occurredAt: string;

  producer: string;

  correlationId: string;

  causationId?: string;

  traceId?: string;

  data: T;
}
```

Example:

```json
{
  "eventId": "evt_123",

  "eventType": "order.created",

  "eventVersion": 1,

  "occurredAt": "2026-09-03T10:00:00.000Z",

  "producer": "order-service",

  "correlationId": "cor_123",

  "causationId": "cmd_123",

  "traceId": "trace_123",

  "data": {
    "orderId": "order_123",
    "userId": "user_123",
    "totalAmount": 249900,
    "currency": "INR"
  }
}
```

This envelope becomes extremely important for debugging distributed systems.

# 23. Publisher Confirms

We should never blindly publish:

```text
channel.publish(...)
```

and assume RabbitMQ received the message.

Instead, publishers should use:

> **Publisher confirms**

Flow:

```text
Order Service
      │
      │ publish
      ▼
RabbitMQ
      │
      │ confirm
      ▼
Order Service
```

If RabbitMQ doesn't confirm:

```text
publish failure
```

must be handled.

---

# 24. Persistent Messages

Messages representing business events should be persistent.

Conceptually:

```typescript
channel.publish(exchange, routingKey, Buffer.from(payload), {
  persistent: true,
});
```

This tells RabbitMQ the message should survive broker restarts when durable queues/exchanges and appropriate disk persistence are configured.

---

# 25. Manual Acknowledgement

Consumers should use:

```text
acknowledgement mode = manual
```

Flow:

```text
RabbitMQ
   │
   ▼
Consumer
   │
   ├── processing succeeds
   │       ↓
   │      ACK
   │
   └── processing fails
           ↓
         retry/DLQ
```

We don't want messages automatically acknowledged before business processing finishes.

```text

    │
    │ max 10 unacknowledged
```

# 33. Retry vs DLQ

A useful rule:

### Retry

Temporary failure:

```text
network timeout
external API unavailable
database temporarily unavailable
```

### DLQ

Permanent or repeatedly failing message:

```text
invalid payload
unsupported event version
business invariant failure
repeated processing failure
```

---

# 34. Idempotency

RabbitMQ provides **at-least-once delivery**, not exactly-once business processing.

Therefore:

```text
Message
   ↓
Consumer
   ↓
Processing
   ↓
ACK
```

could theoretically result in:

```text
processing succeeded
ACK lost
RabbitMQ redelivers
processing happens again
```

Therefore every important consumer must be idempotent.

---

# 35. Consumer Idempotency Key

Every event has:

```text
eventId
```

Example:

```text
evt_123
```

Consumer can store:

```text
processed-event:evt_123
```

or, preferably, use a persistent idempotency record in the service's source-of-truth database when the business operation requires durable deduplication.

Redis can accelerate this, but:

> **Redis alone should not be the authoritative record for critical event processing.**

# 40. RabbitMQ Connection

Create:

```text
packages/messaging/rabbitmq/connection.ts
```

```typescript
import amqp, { Channel, ConfirmChannel, Connection } from "amqplib";

export interface RabbitMQConfig {
  url: string;
}

export interface RabbitMQConnection {
  connection: Connection;
  channel: ConfirmChannel;
}

export async function connectRabbitMQ(
  config: RabbitMQConfig,
): Promise<RabbitMQConnection> {
  const connection = await amqp.connect(config.url);

  const channel = await connection.createConfirmChannel();

  return {
    connection,
    channel,
  };
}
```

# 43. Publisher

Create:

```text
packages/messaging/rabbitmq/publisher.ts
```

```typescript
import { ConfirmChannel } from "amqplib";

import { EventEnvelope } from "./types";

export async function publishEvent<T>(
  channel: ConfirmChannel,
  exchange: string,
  routingKey: string,
  event: EventEnvelope<T>,
): Promise<void> {
  const payload = Buffer.from(JSON.stringify(event));

  channel.publish(exchange, routingKey, payload, {
    persistent: true,
    contentType: "application/json",
    contentEncoding: "utf-8",
    messageId: event.eventId,
    correlationId: event.correlationId,
    timestamp: Date.now(),
  });

  await channel.waitForConfirms();
}
```

# 53. Important Architecture Decision

We are deliberately separating:

```text
RabbitMQ
```

from:

```text
Redis
```

RabbitMQ:

```text
Event/message delivery
```

```text
Cache
Coordination
Locks
Rate limiting
Temporary state
```

Don't use Redis Pub/Sub as a replacement for RabbitMQ in this architecture.

# 54. RabbitMQ Does Not Replace Database Transactions

Suppose:

```text
Order Service
```

does:

```text
INSERT order
```

then:

```text
publish order.created
```

If the database succeeds but RabbitMQ fails:

```text
Database ✅
RabbitMQ ❌
```

we have an inconsistency.

This is exactly why our architecture includes the:

> **Transactional Outbox Pattern**

that we designed earlier.

Eventually:

```text
PostgreSQL Transaction
        │
        ├── orders
        │
        └── outbox_events
                  │
                  ▼
            Outbox Publisher
                  │
                  ▼
               RabbitMQ
```

We will implement that when we reach the relevant service/application phase.


This gives us a robust failure path instead of silently losing events.
