# Phase 0.4.5 — Redis Infrastructure

Now we implement **Redis properly as a shared infrastructure component**, not just as a cache.

In our e-commerce system Redis will support:

```text
Redis
│
├── Application Cache
├── Rate Limiting
├── Idempotency
├── Distributed Locks
├── Session / temporary data
├── Inventory Reservation support
├── Short-lived state
└── Cache invalidation
```

The important principle is:

> **Redis is never the source of truth for business-critical data.**

PostgreSQL/MongoDB remain our source of truth.

---

# 1. Redis Architecture

Our overall architecture becomes:

```text
                         Redis
                           │
       ┌───────────────────┼───────────────────┐
       │                   │                   │
       ▼                   ▼                   ▼
    Cache             Rate Limiter       Distributed Lock
       │                   │                   │
       ▼                   ▼                   ▼
Product data        API requests       Inventory reservation
```

Later:

```text
Auth Service
      │
      ├── Redis → token/session related temporary state
      │
      └── PostgreSQL → permanent user data
```

```text
Product Service
      │
      ├── Redis → product cache
      │
      └── MongoDB → source of truth
```

```text
Inventory Service
      │
      ├── Redis → reservation/lock support
      │
      └── PostgreSQL → inventory source of truth
```

# 3. Why AOF?

We enabled:

```text
--appendonly yes
```

Redis then maintains an append-only log.

Conceptually:

```text
SET user:123 ...
SET product:123 ...
DEL product:123
```

are persisted as operations.

This gives Redis better recovery behavior than relying purely on memory snapshots.

However:

> We still don't treat Redis as our permanent database.

For example, if Redis completely disappears:

```text
Redis ❌
```

our application should recover from:

```text
PostgreSQL ✅
MongoDB ✅
```

# 8. Redis Client

Create:

```text
packages/infrastructure/redis/client.ts
```

```typescript
import Redis from "ioredis";

export interface RedisConfig {
  url: string;
}

export function createRedisClient(config: RedisConfig): Redis {
  const client = new Redis(config.url, {
    maxRetriesPerRequest: 3,

    enableReadyCheck: true,

    retryStrategy(times) {
      const delay = Math.min(times * 100, 2000);

      return delay;
    },
  });

  return client;
}
```

---

# 9. Why Retry?

Suppose:

```text
Order Service
     │
     ↓
Redis
     X
Redis temporarily unavailable
```

We don't immediately want:

```text
Application → crash
```

Instead:

```text
Application
     │
     ↓
Redis connection failure
     │
     ↓
Retry
     │
     ↓
Retry
     │
     ↓
Redis recovered
```

But retries must be bounded.

That's why:

```typescript
maxRetriesPerRequest: 3;
```

is important.

# 15. Cache-Aside Pattern

We'll use:

> **Cache Aside**

Example:

```typescript
const cacheKey = `product:product:${productId}`;
```

First:

```typescript
const cached = await redis.get(cacheKey);
```

If found:

```typescript
return JSON.parse(cached);
```

If not:

```typescript
const product = await Product.findById(productId);
```

Then:

```typescript
await redis.set(cacheKey, JSON.stringify(product), "EX", 300);
```

Now the cache lives for:

```text
5 minutes
```

---

# 16. Why TTL?

Never cache indefinitely unless there is a very specific reason.

Without TTL:

```text
MongoDB
    ↓
Product changes
    ↓
Redis still contains old data
    ↓
Users receive stale data forever
```

With:

```text
TTL = 300 seconds
```

stale data eventually disappears.

But TTL alone isn't enough.

---

# 17. Cache Invalidation

When Product Service updates a product:

```text
Update MongoDB
      │
      ↓
Delete Redis cache
```

Example:

```typescript
await Product.findByIdAndUpdate(productId, update);

await redis.del(`product:product:${productId}`);
```

So:

```text
WRITE
  │
  ├── MongoDB
  │
  └── Redis invalidation
```

Our approach:

```text
Database = source of truth
Redis = acceleration layer
```

If Redis contains stale data:

```text

```

If Redis disappears:

```text

```

This is exactly how we want our system to behave.

# 19. Cache Failure Strategy

What happens if Redis is down?

We should **not** make Product Service completely unavailable.

Instead:

```text
Product request
      │
      ↓
Redis
      X
      │
      ↓
Fallback to MongoDB
```

Example:

```typescript
let cached;

try {
  cached = await redis.get(cacheKey);
} catch (error) {
  logger.warn("Redis unavailable");
}

if (cached) {
  return JSON.parse(cached);
}

return Product.findById(productId);
```

This is called:

> **Graceful cache degradation.**

# 21. Rate Limiting

Redis will also power distributed rate limiting.

Imagine:

```text
API Gateway
     │
     ├── Server 1
     ├── Server 2
     └── Server 3
```

If each server maintains an in-memory counter:

```text
Server 1 → 10 requests
Server 2 → 10 requests
Server 3 → 10 requests
```

the user can effectively make:

```text
30 requests
```

instead of:

```text
10
```

Redis solves this because all instances share the same counter.

# 23. Basic Redis Rate Limit

Conceptually:

```text
Request
   │
   ↓
INCR ratelimit:user:123
   │
   ├── 1
   ├── 2
   ├── 3
   └── ...
```

When it reaches:

```text
100
```

we reject the request.

Set expiry:

```text
EXPIRE ratelimit:user:123 60
```

---

# 24. Atomicity Problem

Don't do this independently:

```text
INCR
EXPIRE
```

because the application could crash between the two operations.

Better:

```text
Lua script
```

or another atomic Redis operation strategy.

We'll implement the production-ready rate limiter when we build API Gateway.

# 25. Distributed Locks

Redis can help us coordinate operations across service instances.

Example:

```text
Inventory Service
```

running:

```text
3 instances
```

A request attempts to reserve:

```text
Product 123
```

Without coordination:

```text
Instance A → reserve
Instance B → reserve
```

Both may race.

A distributed lock can help:

```text
lock:inventory:product:123
```

Conceptually:

```text
Instance A
    │
    ↓
Acquire lock
    │
    ↓
Redis
    │
    ↓
SUCCESS
```

Instance B:

```text
Acquire lock
    ↓
FAILED
```

---

# 26. Redis Lock Must Have TTL

Never create a lock without expiration.

Bad:

```text
SET lock:product:123 locked
```

If the process crashes:

```text
lock remains forever
```

Good:

```text
SET lock:product:123 token NX EX 5
```

Meaning:

```text
NX → only if key doesn't exist
EX 5 → expires in 5 seconds
```

---

# 27. Lock Ownership

We should generate a unique token:

```typescript
const token = crypto.randomUUID();
```

Then:

```text
lock:inventory:product:123
      ↓
token = abc-123
```

Only the owner of the lock should be allowed to release it.

We'll use a Lua script for safe release.

Suppose:

```text

```

Without expiration:


# 35. Shared Cache Wrapper

Create:

```text
packages/infrastructure/redis/cache.ts
```

```typescript
import type Redis from "ioredis";

export class RedisCache {
  constructor(private readonly redis: Redis) {}

  async get<T>(key: string): Promise<T | null> {
    const value = await this.redis.get(key);

    if (!value) {
      return null;
    }

    return JSON.parse(value) as T;
  }

  async set<T>(key: string, value: T, ttlSeconds: number): Promise<void> {
    await this.redis.set(key, JSON.stringify(value), "EX", ttlSeconds);
  }

  async delete(key: string): Promise<void> {
    await this.redis.del(key);
  }
}
```

# 42. Redis Persistence vs Cache

This distinction is important.

Some Redis data is disposable:

```text
product cache
category cache
```

If Redis loses it:

```text
→ database rebuilds it
```

Other data has operational importance:

```text
idempotency
locks
reservation coordination
```

If lost, application logic must still remain correct.

Therefore:

```text
Redis persistence
        ≠
business-data durability
```

Our system must always remain correct even after Redis loses its data.
