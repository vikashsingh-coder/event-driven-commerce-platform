# Phase 0.4.4 — MongoDB Infrastructure

Now we’ll make MongoDB **application-ready**, just like we did with PostgreSQL.

The important architectural decision is:

> **MongoDB will be used by Product, Notification, and Analytics services, with each service owning its own database.**

---

# 1. MongoDB Architecture

Our current database architecture becomes:

```text
                         MongoDB 8
                            │
          ┌─────────────────┼─────────────────┐
          │                 │                 │
          ▼                 ▼                 ▼
   ecommerce_products   ecommerce_notifications

                         ecommerce_analytics
```

Service ownership:

```text
Product Service
      │
      ▼
ecommerce_products


Notification Service
      │
      ▼
ecommerce_notifications


Analytics Service
      │
      ▼
ecommerce_analytics
```

Just like PostgreSQL:

```text
❌ Product Service → Notification DB
❌ Order Service → Product DB
❌ Analytics Service → Order DB
```

Services communicate through APIs/events instead.

---

# 2. Why MongoDB for These Services?

We deliberately chose different database technologies based on workload.

### Product

Product documents can have flexible attributes:

```json
{
  "name": "iPhone 17",
  "categoryId": "...",
  "price": 89999,
  "attributes": {
    "color": "Black",
    "storage": "256GB",
    "ram": "8GB"
  }
}
```

Different product categories may have completely different attributes.

MongoDB handles this naturally.

### Notification

Notifications can contain different payloads:

```text
Email
SMS
Push
WhatsApp
```

Their metadata isn't necessarily identical.

### Analytics

Analytics data can evolve rapidly and often contains semi-structured event data.

MongoDB gives us flexibility here.

# 5. MongoDB Initialization Script

Create:

```text
infrastructure/mongodb/init/01-create-databases.js
```

Use:

```javascript
const databases = [
  "ecommerce_products",
  "ecommerce_notifications",
  "ecommerce_analytics",
];

databases.forEach((databaseName) => {
  const database = db.getSiblingDB(databaseName);

  database.createCollection("_initialization");

  database._initialization.insertOne({
    initialized: true,
    initializedAt: new Date(),
  });

  database._initialization.drop();
});
```

---

# 6. Why Are We Creating a Temporary Collection?

MongoDB creates databases lazily.

Unlike PostgreSQL:

```sql
CREATE DATABASE ecommerce_products;
```

MongoDB doesn't have the same database-creation workflow.

A database effectively exists when data is written to it.

So:

```javascript
db.getSiblingDB("ecommerce_products");
```

followed by:

```javascript
createCollection();
```

ensures the database is materialized.

# 14. MongoDB Connection Module

Create a reusable database connection inside the service.

For Product Service:

```text
apps/product-service/src/infrastructure/database/
├── mongodb.ts
└── index.ts
```

`mongodb.ts`:

```typescript
import mongoose from "mongoose";

export async function connectMongoDB(connectionString: string): Promise<void> {
  await mongoose.connect(connectionString, {
    serverSelectionTimeoutMS: 5000,
    maxPoolSize: 10,
    minPoolSize: 2,
  });

  console.log("MongoDB connected successfully");
}
```

---

# 15. Why `maxPoolSize`?

Suppose Product Service receives:

```text
1000 requests
```

We don't want:

```text
1000 MongoDB connections
```

Instead:

```text
1000 requests
      │
      ↓
Mongoose
      │
      ↓
Connection Pool
      │
      ├── Connection 1
      ├── Connection 2
      ├── ...
      └── Connection 10
```

Our initial configuration:

```typescript
maxPoolSize: 10;
```

is suitable for local development.

We'll tune this based on actual production workload.

---

# 16. Minimum Pool Size

We also set:

```typescript
minPoolSize: 2;
```

This means the application attempts to maintain a small pool of ready connections.

This reduces connection setup overhead during normal traffic.

---

# 17. MongoDB Connection Timeout

We use:

```typescript
serverSelectionTimeoutMS: 5000;
```

Meaning:

```text
Application
    ↓
MongoDB unavailable
    ↓
Try server selection
    ↓
5 seconds
    ↓
Failure
```

Without appropriate timeout configuration, a service can appear to hang when MongoDB isn't available.

# 20. Better Health Check

For a real readiness check, we should actually ping MongoDB.

```typescript
import mongoose from "mongoose";

export async function checkMongoDB(): Promise<void> {
  const connection = mongoose.connection;

  if (!connection.db) {
    throw new Error("MongoDB connection is not ready");
  }

  await connection.db.command({
    ping: 1,
  });
}
```

This verifies that MongoDB is actually responding.

# 23. Important: Money Handling

Don't eventually store financial values like:

```text
89999.99
```

using floating-point arithmetic blindly.

For our commerce system, we should use:

```text
integer minor units
```

For INR:

```text
₹899.99
```

becomes:

```text
89999 paise
```

So the database can contain:

```json
{
  "price": 89999,
  "currency": "INR"
}
```

This avoids floating-point precision problems.

This same principle will be used for:

```text
Product prices
Order totals
Payment amounts
Refund amounts
Coupon discounts
```

# 29. MongoDB Transactions

MongoDB supports transactions, but we should not automatically use transactions everywhere.

For example:

```text
Create Product
```

usually requires only one document write.

No transaction needed.

But if we have a multi-document atomic operation:

```text
Update Product
+
Create audit record
```

then a transaction may make sense.

However:

```text
MongoDB transaction
+
PostgreSQL transaction
+
RabbitMQ publish
```

is **not** one distributed transaction.

Our distributed consistency remains based on:

```text
Saga
Outbox
Events
Idempotency
```

# 31. MongoDB Authentication

We're using:

```yaml
MONGO_INITDB_ROOT_USERNAME
MONGO_INITDB_ROOT_PASSWORD
```

This means MongoDB authentication is enabled.

Our connection uses:

```text
authSource=admin
```

Example:

```text
mongodb://user:password@mongodb:27017/ecommerce_products?authSource=admin
```

Without:

```text
authSource=admin
```

authentication may fail because the root user was created in the `admin` database.

# 32. Don't Use Root Credentials in Production

Currently:

```text
ecommerce
```

is our development MongoDB user.

Production should eventually use:

```text
product_service_user
notification_service_user
analytics_service_user
```

with limited privileges.

For example:

```text
product_service_user
      ↓
ecommerce_products
```

and not:

```text
product_service_user
      ↓
ALL DATABASES
```

We'll implement this during security/deployment hardening.
