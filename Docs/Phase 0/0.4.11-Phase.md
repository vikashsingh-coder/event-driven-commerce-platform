# 11. Service Startup

We should not blindly start every service at exactly the same time.

Instead:

```text
Infrastructure
     ↓
Health checks
     ↓
Database ready
     ↓
Redis ready
     ↓
RabbitMQ ready
     ↓
Services start
```

However, the services themselves must still handle temporary dependency failures gracefully.

We should **not** rely solely on startup ordering.

---

# 12. Docker `depends_on`

Docker Compose can express:

```yaml
depends_on:
  postgres:
    condition: service_healthy
```

For example:

```yaml
services:
  order-service:
    depends_on:
      postgres:
        condition: service_healthy

      redis:
        condition: service_healthy

      rabbitmq:
        condition: service_healthy
```

This improves local startup reliability.

---

# 13. But `depends_on` Is Not Enough

This is important.

Even with:

```yaml
depends_on:
```

the application must still handle:

```text
Database connection lost
Redis temporarily unavailable
RabbitMQ reconnecting
```

because infrastructure can fail **after startup**.

So:

```text
Docker startup ordering
        +
Application retry/reconnect
```

are both required.

# 15. Migration Ownership

Each service owns its database schema.

For example:

```text
Auth Service
    ↓

    ↓
order_db

    ↓

```

The Order Service should **not** directly modify the Payment Service's database.

# 18. Seed Data Must Be Idempotent

Running:

```bash
pnpm db:seed
```

twice should **not** create duplicates.

Bad:

```text
Run seed
→ 10 products

Run seed again
→ 20 products
```

Good:

```text
Run seed
→ 10 products

Run again
→ still 10 products
```

Use deterministic IDs or unique keys/upserts.
