# Phase 0.4.7 — Nginx Infrastructure

Now we'll introduce **Nginx as the API Gateway / reverse proxy layer** in front of our microservices.

The objective is not just to make Nginx forward requests. We want a clean foundation for:

- Reverse proxying
- Service routing
- Centralized entry point
- Rate limiting foundation
- Request size limits
- Timeouts
- Security headers
- Health routing
- WebSocket support
- Docker networking
- Future TLS/HTTPS
- Load balancing
- Service isolation

---

# 1. Target Architecture

Our infrastructure now becomes:

```text
                         Internet / Client
                                │
                                ▼
                         ┌────────────┐
                         │   Nginx    │
                         │ API Gateway│
                         └──────┬─────┘
                                │
              ┌─────────────────┼─────────────────┐
              │                 │                 │
              ▼                 ▼                 ▼
        Auth Service      Product Service    Order Service
              │                 │                 │
              ▼                 ▼                 ▼
         PostgreSQL          MongoDB          PostgreSQL
```

And:

```text
Nginx
 │
 ├── /api/v1/auth/*
 │       ↓
 │   Auth Service
 │
 ├── /api/v1/products/*
 │       ↓
 │   Product Service
 │
 ├── /api/v1/categories/*
 │       ↓
 │   Product Service
 │
 ├── /api/v1/orders/*
 │       ↓
 │   Order Service
 │
 ├── /api/v1/payments/*
 │       ↓
 │   Payment Service
 │
 └── /api/v1/reviews/*
         ↓
     Product Service
```

The client should **not directly communicate with individual services**.

---

# 2. Why Nginx?

Without Nginx:

```text
Client
 ├── localhost:3001 → Auth
 ├── localhost:3002 → Product
 ├── localhost:3003 → Order
 └── localhost:3004 → Payment
```

This exposes internal architecture.

With Nginx:

```text
Client
   │
   ▼
api.example.com
   │
   ▼
Nginx
   │
   ├── Auth
   ├── Product
   ├── Order
   └── Payment
```

The client sees **one API endpoint**.

---

# 3. Nginx Responsibilities

Our Nginx layer will initially handle:

```text
                 Nginx
                   │
       ┌───────────┼────────────┐
       │           │            │
       ▼           ▼            ▼
    Routing     Security     Traffic
       │           │            │
       ├─ Proxy    ├─ Headers  ├─ Limits
       ├─ Rewrite  ├─ Hide     ├─ Timeouts
       └─ Upstream └─ CORS*    └─ Load balancing
```

`*` We'll keep CORS policy primarily at the application layer and use Nginx only where appropriate.

# 10. Worker Processes

```nginx
worker_processes auto;
```

means Nginx determines a suitable number of worker processes based on available CPU.

This is better than hardcoding:

```nginx
worker_processes 1;
```

for production.

# 11. Connection Limit

```nginx

    worker_connections 1024;
```

This determines how many connections each worker can handle.


# 19. The Important `proxy_pass` Detail

Consider:

```nginx
location /api/v1/products/ {
    proxy_pass http://product_service/;
}
```

The trailing `/` matters.

It means Nginx removes the matching location prefix.

For example:

```text
Client:

/api/v1/products/123
```

can become:

```text
/123
```

at the upstream.

Whether we want this behavior depends on our service API contract.

### Better decision for our project

Our internal services should expose their own clean routes:

```text
GET /products/:id
```

while the public API is:

```text
GET /api/v1/products/:id
```

So the stripping behavior is intentional.

# 22. Request ID

We want every incoming request to have a request identifier.

Nginx can generate:

```nginx
add_header X-Request-ID $request_id always;
```

But for distributed tracing, we eventually want to **propagate an existing request/trace ID when supplied**, rather than blindly generating a new identifier at every layer.

Our application middleware will eventually standardize this.

For now:

```nginx
proxy_set_header X-Request-ID $request_id;
```

---

# 23. Timeouts

Never allow upstream requests to hang indefinitely.

Add:

```nginx
proxy_connect_timeout 5s;

proxy_send_timeout 30s;

proxy_read_timeout 30s;
```

Meaning:

```text
Connect to service
→ 5 seconds

Send request
→ 30 seconds

Wait for response
→ 30 seconds
```

---

# 24. Request Body Size

E-commerce APIs may receive:

```text
JSON
images
documents
```

We should explicitly control request size.

Initial value:

```nginx
client_max_body_size 10m;
```

For normal API requests this is already generous.

File uploads should eventually use a dedicated upload strategy rather than allowing arbitrarily large API requests.

---

# 25. Security Headers

Add:

```nginx
add_header X-Content-Type-Options "nosniff" always;

add_header X-Frame-Options "DENY" always;

add_header Referrer-Policy "strict-origin-when-cross-origin" always;
```

For HTTPS production we'll add a properly configured:

```text
Strict-Transport-Security
```

only after TLS is actually enabled.

Do **not** enable HSTS casually on a local HTTP environment.

---

# 26. Disable Unnecessary Methods

For APIs, we can explicitly control methods at sensitive routes.

For example:

```nginx
limit_except GET POST PUT PATCH DELETE OPTIONS {
    deny all;
}
```

But we don't need to put this globally yet.

The application itself must also enforce HTTP methods.

# 27. Rate Limiting Foundation

Nginx can provide an outer rate limit.

Example:

```nginx
limit_req_zone
$binary_remote_addr
zone=api_limit:10m
rate=10r/s;
```

Then:

```nginx
limit_req
zone=api_limit
burst=20
nodelay;
```

Conceptually:

```text
Client
   │
   ▼
Nginx
   │
   │ 10 requests/sec
   ▼
Microservices
```

# 28. But We Already Have Redis

Yes.

Our architecture deliberately has **two levels** of traffic protection.

### Nginx

Protects infrastructure:

```text
Internet
 ↓
Nginx
 ↓
services
```

### Redis-backed application rate limiter

Protects business APIs:

```text
Nginx
 ↓
API Gateway / Service
 ↓
Redis
```

This allows more sophisticated limits such as:

```text
anonymous IP
authenticated user
admin
payment endpoint
login endpoint
```

So Nginx's rate limiter is only the **first defensive layer**.

```text

```

returns:

```text

```

This tells us:

```text

```

It does **not** mean every backend service is healthy.

We should distinguish:

```text
/health
```

from:

```text
/ready
```

### Health

```text
Nginx process alive
```

### Ready

Eventually:

```text
Nginx
 │
 ├── Auth healthy
 ├── Product healthy
 ├── Order healthy
 └── Payment healthy
```

For now we'll keep Nginx health simple.

Service-specific health checks will be implemented when we create the service template.

# 32. Error Handling

Nginx should return sensible gateway errors.

For example:

```text
502
```

means:

```text
Bad Gateway
```

typically indicating upstream communication failure.

```text
504
```

means:

```text
Gateway Timeout
```

We'll keep the default Nginx error behavior initially and later standardize our API error envelope at the application layer.

---

# 33. Do Not Transform Application Errors in Nginx

Suppose Product Service returns:

```json
{
  "error": {
    "code": "PRODUCT_NOT_FOUND",
    "message": "Product not found"
  }
}
```

Nginx should normally pass that through.

We don't want:

```text
Nginx
 ↓
rewrite everything
```

because application services own business errors.

Nginx owns:

```text
network-level errors
```

while services own:

```text
business-level errors
```

# 35. Internal Services Must Not Be Public

Eventually our Docker architecture should be:

```text
Internet
   │
   ▼
Nginx :80
   │
   ▼
Internal services
```

Not:

```text
Internet
 ├── :3001 Auth
 ├── :3002 Product
 ├── :3003 Order
 └── :3004 Payment
```

Therefore service ports should eventually **not be published to the host** unless required for local debugging.

Example:

Bad production-style compose:

```yaml
ports:
  - "3001:3001"
```

Better:

```yaml
expose:
  - "3001"
```

Then only Docker-network clients can access the service.

```text
services/
├── auth-service/
├── product-service/
├── order-service/
├── payment-service/
├── notification-service/
└── analytics-service/
```

Each service will get the same foundation for:

```text
Express
TypeScript
configuration
logging
error handling
validation
health checks
graceful shutdown
Redis
RabbitMQ
database connection
testing
Dockerfile
ESLint
Prettier
request IDs
OpenTelemetry-ready tracing
```

That will allow us to stop configuring infrastructure manually and start **actually building the microservices**.
