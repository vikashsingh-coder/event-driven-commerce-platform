# 1. PostgreSQL Architecture

We're deliberately **not** going to create one giant database schema containing every microservice's tables.

Our logical ownership is:

```text
PostgreSQL Cluster
│
├── ecommerce_auth
│   ├── users
│   ├── roles
│   ├── permissions
│   ├── user_roles
│   └── refresh_tokens
│
├── ecommerce_inventory
│   ├── inventories
│   ├── inventory_reservations
│   └── inventory_movements
│
├── ecommerce_orders
│   ├── orders
│   ├── order_items
│   └── order_status_history
│
└── ecommerce_payments
    ├── payments
    ├── payment_transactions
    └── refunds
```

The important rule is:

> **A service owns its database. Other services never directly query its tables.**

For example:

```text
Order Service
     │
     X
     │
     └──────> inventory database ❌
```

Instead:

```text
Order Service
     │
     │ RabbitMQ
     ↓
Inventory Service
     │
     ↓
Inventory Database
```

This keeps our microservices actually decoupled.

# 3. One PostgreSQL Container vs Multiple Containers

For local development, we'll use:

```text

                     │
                     ├── ecommerce_auth
                     ├── ecommerce_inventory
                     ├── ecommerce_orders
                     └── ecommerce_payments
```

This is much lighter than running four PostgreSQL containers.

But logically:

```text
Auth Service
    ↓

    ↓

```

The databases remain isolated at the application level.

Later in production, these databases can be moved to separate PostgreSQL instances/clusters if required.

# 5. Mount Initialization Script

Update PostgreSQL in:

```text
docker-compose.yml
```

Add:

```yaml
volumes:
  - postgres_data:/var/lib/postgresql/data
  - ./infrastructure/postgres/init:/docker-entrypoint-initdb.d:ro
```

So the complete PostgreSQL section becomes:

```yaml
postgres:
  image: postgres:17-alpine

  container_name: ecommerce-postgres

  restart: unless-stopped

  environment:
    POSTGRES_USER: ${POSTGRES_USER}
    POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    POSTGRES_DB: ${POSTGRES_DB}

  ports:
    - "${POSTGRES_PORT}:5432"

  volumes:
    - postgres_data:/var/lib/postgresql/data
    - ./infrastructure/postgres/init:/docker-entrypoint-initdb.d:ro

  networks:
    - infra-network

  deploy:
    resources:
      limits:
        cpus: "1.0"
        memory: 1G

  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]

    interval: 5s
    timeout: 5s
    retries: 10
    start_period: 10s
```

# 6. Important Docker Behavior

PostgreSQL executes:

```text
/docker-entrypoint-initdb.d/*
```

**only when the database directory is initialized for the first time.**

So if PostgreSQL is already running with an existing volume:

```bash
docker compose up
```

will **not** execute the new SQL file.

For our development environment, reset it:

```bash
docker compose down -v
```

Then:

```bash
docker compose up -d
```

# 10. Docker Internal URLs

When services run inside Docker, `localhost` changes meaning.

Inside:

```text
order-service
```

this:

```text
localhost:5432
```

means:

> the Order Service container itself.

That's wrong.

We need:

```text
postgres:5432
```

Therefore eventually we'll have:

```env
ORDER_DATABASE_URL=postgresql://ecommerce:ecommerce_dev_password@postgres:5432/ecommerce_orders
```

for Docker.

And:

```env
ORDER_DATABASE_URL=postgresql://ecommerce:ecommerce_dev_password@localhost:5432/ecommerce_orders
```

for host-based development.

We'll handle this cleanly through environment profiles in a later infrastructure step.

Suppose Order Service has:

```text

order_items
```

Inventory Service has:

```text

inventory_reservations
```

If we put everything into one Prisma schema:

```text

```

we create accidental coupling.

Instead:

```text

    ↓
Order Prisma Client
    ↓
Order Database
```

and:

```text
Inventory Service
    ↓
Inventory Prisma Client
    ↓
Inventory Database
```

This matches our microservice architecture.

# 22. Transaction Strategy

Transactions are allowed **inside a service's database boundary**.

For example:

```text
Order Service
    │
    ├── create order
    ├── create order items
    └── create outbox event
          │
          ↓
       COMMIT
```

All three can happen in one PostgreSQL transaction.

But we should **not** attempt:

```text
PostgreSQL
     +
MongoDB
     +
RabbitMQ
```

inside one database transaction.

That's exactly why we designed:

```text
Saga
+
Outbox
+
Event-driven architecture
```

earlier.

---

# 23. Example Transaction

Eventually:

```typescript
await prisma.$transaction(async (tx) => {
  const order = await tx.order.create({
    data: orderData,
  });

  await tx.orderItem.createMany({
    data: orderItems,
  });

  await tx.outboxEvent.create({
    data: {
      eventType: "order.created",

      aggregateId: order.id,

      payload: JSON.stringify(orderCreatedEvent),
    },
  });
});
```

The important property:

```text
Order created
      +
Event stored
      ↓
     COMMIT
```

Either both happen or neither happens.

This prevents the classic:

```text
Order saved
   ↓
RabbitMQ publish failed
   ↓
Order exists
BUT
event doesn't
```

problem.

We'll implement the full transactional outbox when we reach the Order Service.

# 26. Seed Data

We should keep seed data separate from migrations.

Example:

```text
apps/auth-service/prisma/seed.ts
```

```typescript
import { PrismaClient } from "@prisma/client";

const prisma = new PrismaClient();

async function main() {
  await prisma.user.create({
    data: {
      email: "admin@example.com",

      password: "REPLACE_WITH_HASH",
    },
  });
}

main()
  .catch(console.error)
  .finally(async () => {
    await prisma.$disconnect();
  });
```

**Never store a plaintext password in a seed.**

We'll use our security package to generate the hash when implementing Auth Service.
