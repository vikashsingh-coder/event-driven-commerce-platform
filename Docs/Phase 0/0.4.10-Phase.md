Let go for Phase 0.4.10

Absolutely. **Phase 0.4.10 — Health Checks** is the point where our services become properly manageable by Docker, Nginx, and eventually Kubernetes/orchestration.

The important distinction we'll implement is:

> **Liveness answers "Is the process alive?"**  
> **Readiness answers "Can this service safely receive traffic?"**

# Phase 0.4.10 — Health Check Architecture

## 1. Objectives

By the end of this phase, every microservice will expose:

```text
GET /health/live
GET /health/ready
GET /health
```

with:

- Standardized response format
- Liveness checks
- Readiness checks
- Database checks
- Redis checks
- RabbitMQ checks
- Dependency timeout protection
- Docker health checks
- Graceful shutdown integration
- Startup state management
- Proper HTTP status codes
- Structured logging

---

# 2. Why Three Endpoints?

We don't want one endpoint doing everything.

### Liveness

```text
GET /health/live
```

Answers:

> Is the application process alive?

It should be extremely cheap.

```text
Node.js process
      │
      ▼
   Liveness
      │
      ▼
     200
```

It should **not** query PostgreSQL, Redis, or RabbitMQ.

---

### Readiness

```text
GET /health/ready
```

Answers:

> Is the service capable of processing requests?

For Order Service:

```text
Order Service
     │
     ├── PostgreSQL     ✅
     ├── Redis          ✅
     └── RabbitMQ       ✅
          │
          ▼
       READY
```

If PostgreSQL is unavailable:

```text
Order Service
     │
     ├── PostgreSQL     ❌
     ├── Redis          ✅
     └── RabbitMQ       ✅
          │
          ▼
     NOT READY
```

---

### Combined Health

```text
GET /health
```

This gives developers/operators an overall diagnostic view.

# 3. HTTP Status Codes

We'll standardize:

| Endpoint        | Healthy | Unhealthy |
| --------------- | ------: | --------: |
| `/health/live`  |   `200` |     `503` |
| `/health/ready` |   `200` |     `503` |
| `/health`       |   `200` |     `503` |

For readiness:

```text
200 = READY
503 = NOT READY
```

This is important because load balancers and orchestration systems understand `503`.

# 10. Why No Dependencies?

Imagine PostgreSQL goes down.

If `/health/live` checks PostgreSQL:

```text
PostgreSQL ❌
     ↓
/health/live ❌
     ↓
Orchestrator thinks
Node.js is dead
     ↓
Restart container
```

But Node.js itself may be perfectly healthy.

That's incorrect.

Instead:

```text
PostgreSQL ❌
     ↓
/health/ready ❌
     ↓
Remove service from traffic
```

while:

```text
/health/live
     ↓
200
```

The process remains alive.

# 13. RabbitMQ Health Check

RabbitMQ is slightly different.

We shouldn't create a brand-new RabbitMQ connection every time `/health/ready` is called.

Instead, the messaging layer maintains connection state.

Conceptually:

```typescript
export function checkRabbitMQ(rabbitmq: RabbitMQClient): "up" | "down" {
  return rabbitmq.isConnected() ? "up" : "down";
}
```

# 16. Readiness Implementation

Conceptually:

```typescript
async getReadiness(): Promise<HealthResponse> {

  const database =
    await checkDatabase(this.database);

  const redis =
    await checkRedis(this.redis);

  const rabbitmq =
    checkRabbitMQ(this.rabbitmq);

  const ready =
    database === "up" &&
    redis === "up" &&
    rabbitmq === "up";

  return {
    status: ready ? "ok" : "error",

    service: this.serviceName,

    timestamp:
      new Date().toISOString(),

    checks: {
      database,
      redis,
      rabbitmq,
    },
  };
}
```

# 17. Health Controller

```typescript
export class HealthController {
  constructor(private readonly healthService: HealthService) {}

  live = (_req, res) => {
    const result = this.healthService.getLiveness();

    return res.status(200).json(result);
  };

  ready = async (_req, res) => {
    const result = await this.healthService.getReadiness();

    const status = result.status === "ok" ? 200 : 503;

    return res.status(status).json(result);
  };
}
```

# 20. Dependency Timeout

This is extremely important.

Imagine:

```text
PostgreSQL
   │
   │ request hangs
   ▼
SELECT 1
   │
   │ 30 seconds
   ▼
Health endpoint
```

Now Docker waits.

That's bad.

Every dependency check needs a timeout.

Example:

```typescript
const HEALTH_CHECK_TIMEOUT = 2000;
```

So:

```text
Health check
     │
     ├── dependency responds < 2s
     │        ↓
     │       UP
     │
     └── timeout
              ↓
             DOWN
```

---

# 21. Generic Timeout Helper

```typescript
export async function withTimeout<T>(
  promise: Promise<T>,
  timeoutMs: number,
): Promise<T> {
  let timeout: NodeJS.Timeout;

  const timeoutPromise = new Promise<never>((_, reject) => {
    timeout = setTimeout(() => {
      reject(new Error("Health check timeout"));
    }, timeoutMs);
  });

  try {
    return await Promise.race([promise, timeoutPromise]);
  } finally {
    clearTimeout(timeout!);
  }
}
```

Then:

```typescript
await withTimeout(database.query("SELECT 1"), 2000);
```

# 22. Parallel Dependency Checks

Don't check:

```text
Database
   ↓
wait
   ↓
Redis
   ↓
wait
   ↓
RabbitMQ
```

Instead:

```text
             ┌── Database
             │
Health ──────┼── Redis
             │
             └── RabbitMQ
```

Using:

```typescript
const [database, redis, rabbitmq] = await Promise.all([
  checkDatabase(),
  checkRedis(),
  checkRabbitMQ(),
]);
```

This reduces readiness-check latency.


We can keep:

```text

```

```text
/health/ready → 503
```

This distinction is exactly why liveness and readiness must be separate.

Docker's job here is primarily:

> Is the process/container functioning?

So:

```text
Docker
  ↓
```

not:

```text

  ↓
```

# 42. Health Service with Generic Checks

```typescript
export class HealthService {
  constructor(
    private readonly serviceName: string,
    private readonly checks: HealthCheck[],
  ) {}

  async checkReadiness() {
    const results = await Promise.all(
      this.checks.map(async (check) => {
        const status = await check.check();

        return [check.name, status];
      }),
    );

    const checks = Object.fromEntries(results);

    const ready = Object.values(checks).every((status) => status === "up");

    return {
      status: ready ? "ok" : "error",

      service: this.serviceName,

      timestamp: new Date().toISOString(),

      checks,
    };
  }
}
```

This gives us a reusable framework.
